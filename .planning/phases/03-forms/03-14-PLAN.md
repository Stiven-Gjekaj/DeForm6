<objective>
Find the scope-separator rule for closing a menu nested two levels deep back
to a sibling menu at the form's own top level, then replace the defensive
bound that stands in for it.

Purpose: success criterion 1 asks for the control tree of every corpus form.
The tool recovers 49 of 53. The four it does not recover it refuses honestly,
which is the criterion's own third sentence and is correct behaviour. But
"every form" is not met, and the reason is a gap in this repository's
knowledge of the scope-byte grammar, not a defect in the refusal. Plan 03-04
settled the single-level menu case by measuring four real transitions in one
corpus program. This plan does the same for the transition 03-04 did not
cover.

This session measured which forms fail and how, before the plan was written.
Three of the four fail the same way and one fails differently. That
difference is recorded below and this plan keeps the two apart.

Output: a measured rule in `crates/deform6/src/vb/controltree.rs`, re-pinned
counts in `tests/ratios.toml`, and the finding written into
`.planning/research/STRUCTURES.md` and `.planning/WINDOWS.md`.
</objective>

## What this session measured before the plan was written

Every line below came from running the committed binary against the corpus.
**Treat it as a lead, not as a fact.** Take each measurement again and write
your own numbers in the SUMMARY.

| Program | Form | How it fails | Menus in the committed `.frm` |
|---|---|---|---|
| `corpus/public-domain/HexScroll/Hex Scroll.exe` | `FrmHex` | the walk would leave 141 bytes unaccounted at file offset `0x16ff` | 6, in two top level groups, each with children |
| `corpus/public-domain/UUID2/VB6/UUID2.exe` | `frmUUID2` | the walk would leave 251 bytes unaccounted at file offset `0x191a` | 8, in three top level groups, each with children |
| `corpus/public-domain/PassGen/PassGen.exe` | `frmPassGen` | the walk would leave 496 bytes unaccounted at file offset `0x2058` | 14 |
| `corpus/vb6-code/Map-editor-2D/Map Editor.exe` | `Main` | a scope separator was expected at file offset `0x170e` and the byte there is `0x37` | 12 |

**The fourth is a different failure.** It never reaches the tail bound at all.
It stops earlier, at a position where the walk expected a separator byte and
found something else. Do not assume one rule explains both. Measure the fourth
separately and report what you find, even when what you find is that it is
still open.

The shape the three tail failures share, read from the committed `.frm` files:
a top level menu with a child, then a second top level menu that also has
children. `corpus/vb6-code/Grayscale-effect/Grayscale.exe`, the program plan
03-04 measured, has one top level menu with children and no second one. That
is exactly the transition 03-04 never saw.
