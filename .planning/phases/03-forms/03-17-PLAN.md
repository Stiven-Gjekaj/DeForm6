## What this session measured before the plan was written

**Treat every number as a lead.** Take each measurement again and write your
own in the SUMMARY.

`Refusal::Damaged` takes a string with a static lifetime. There are 143
construction sites of that variant across 13 files. Three of those files also
carry a byte for byte identical private helper that leaks a heap string to
satisfy the lifetime:

    crates/deform6/src/vb/gui.rs
    crates/deform6/src/vb/controltree.rs
    crates/deform6/src/vb/frx.rs

Widening the variant to carry an owned string would remove the leak
completely and would touch all 143 sites. Extracting one shared helper
centralises the leak without removing it and touches four files. The review's
own stated fix is the second one, and its stated reason is that a later
decision to widen the variant then touches one call site instead of three.

**Decide with the numbers in front of you and record the decision.** Both
answers are defensible. What is not defensible is choosing one without saying
which cost you accepted.

## Scope note: the fuzzing gate is not in this plan

`AGENTS.md` says fuzzing is part of the gate. There is no fuzz target in this
repository and the review's own finding WR-01 reasons about a fuzz host that
does not yet exist. That is not silently dropped and it is not this gap run's
work: `.planning/REQUIREMENTS.md` maps it to SAF-05, and `ROADMAP.md` Phase 5
owns it by name, together with `--salvage` and the run-time robustness corpus.
The one thing this gap run can usefully do for it is the leak finding above,
because a fuzz host is exactly what turns that leak into unbounded growth.
Note the reasoning in the SUMMARY so the connection is on record when phase 5
starts.
