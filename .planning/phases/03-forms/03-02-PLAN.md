## One representation, two sources

The table can come from two places: the builtin subset compiled into the
crate, and a file the user built on their own machine. These are not two
types and not two code paths.

`OpcodeTable` is the one representation. `OpcodeTable::builtin` builds it from
constants. `OpcodeTable::parse` builds it from bytes. `OpcodeTable::lookup`
takes the same input and gives the same answer whichever constructor built it.

The general representation is the primary one, and the builtin subset is one
way of constructing it. Do not add a second lookup path for the builtin case.
A second path is where a table that works one way and fails the other hides.

<task type="checkpoint:decision" gate="blocking">
  <decision>Choose the on-disk format of the opcode table</decision>
  <context>
    Per D-01, DeForm6 ships with no opcode table. A user builds one on their
    own machine and passes it with `--opcode-table <path>`. The format is
    therefore a published contract between the derivation tool and every
    table any user has already built. Changing it later invalidates every
    such table and every script that writes one. This is a one-way door and
    it is not covered by D-01, which fixed the flag but not the file syntax.

    The table holds one row per pair: a control type, an opcode number, a
    payload type, and a property name. `03-RESEARCH.md` counts 198 pairs
    across 20 control types as the corpus relevant target.
  </context>
  <options>
    <option id="toml">
      <name>TOML, one table per control type, keyed by opcode</name>
      <pros>`toml` 1.1.5 is already a workspace dependency and `xtask` already uses it. `tests/ratios.toml` gives this repository a precedent a reader already knows. A schema, real parse errors with line and column, and a user can hand-edit one row to close one pair, which is the workflow D-01 expects. `serde` is already a `deform6` dependency, so only `toml` is added.</pros>
      <cons>Adds `toml` to the `deform6` library crate, which today depends only on `object`, `thiserror` and `serde`. A parser dependency inside the library that reads hostile files widens the surface phase 5 has to fuzz.</cons>
    </option>
    <option id="lines">
      <name>A line oriented text format, one record per line, four fields separated by whitespace</name>
      <pros>Adds no dependency at all to the `deform6` crate, which keeps the fuzz surface exactly as small as it is today. A shell script or a spreadsheet export can produce it. Appending one line to close one pair needs no tool. The parser is small enough to read in one sitting and to reason about for hostility.</pros>
      <cons>No schema. DeForm6 writes its own parser and its own error messages, and every error must carry a line number by hand. A property name that holds a space needs a quoting rule this project then owns.</cons>
    </option>
    <option id="binary">
      <name>A binary format with a magic number and a version field</name>
      <pros>Compact and fast to load. A version field makes a later format change explicit rather than silent.</pros>
      <cons>A user cannot read it, cannot hand-edit it, and cannot close one pair without running the tool. D-01's own follow-up plan is a human closing pairs one at a time, which this format blocks. It also contradicts this repository's stated posture of committing text a human can read.</cons>
    </option>
  </options>
  <resume-signal>Reply with `toml`, `lines`, or `binary`. Task 2 implements the chosen format and no other.</resume-signal>
</task>
