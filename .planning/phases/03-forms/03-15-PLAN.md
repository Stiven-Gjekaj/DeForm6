<objective>
Give `frx::extract_blob` a production call site, carry what it recovers into
the report, and print it, so a live `inspect` surfaces a resource blob.

Purpose: this is the most important gap the phase 3 verification found.
`frx::extract_blob` is substantive and has twenty passing unit tests, and it
has zero production call sites. `walk_properties`'s resource blob arm reports
the opcode as not decoded and stops. `compose_form` and `compose_control`
never mention the module. From the product's point of view the whole reader
is dead code, and no run of the tool has ever surfaced a blob. A unit test on
an uncalled function is exactly what let that through, so the proof this plan
adds runs the production entry point over real corpus bytes.

This session also measured, against three committed `.frx` files, that
`BlobCursor` advances by the wrong amount. That defect is inside the same
capability and phase 4's writer would inherit it, so this plan fixes it first
and proves the fix against the offsets a committed `.frm` declares.

Output: a wired resource blob path, a blob in the report, a blob on the
command line, and an end to end test that fails when the wiring is removed.
</objective>

## What this session measured before the plan was written

**Treat every number as a lead, not as a fact.** Take each measurement again
and write your own numbers in the SUMMARY.

**The blob is inline and the committed `.frx` item is the same bytes.** In
`corpus/vb6-code/Fire-effect/Fast_Flames.exe`, the four byte length field of
the form's own resource blob sits at file offset `0x13d5`. The 1418 bytes
starting there are byte for byte identical to the whole 1418 byte
`corpus/vb6-code/Fire-effect/frmFire.frx`. Laid against `Blob`'s own fields
that reads as: the four bytes at `frx[0..4]` are the declared length, the
eight bytes at `frx[4..12]` are `Blob::header`, and `frx[12..]` is
`Blob::image`.

**`BlobCursor::take` advances by the wrong amount.**
`corpus/vb6-code/Game-physics-basic/FormPhysics.frm` declares ten resource
offsets into `FormPhysics.frx`, from `0000` to `C757`. Reading the declared
length at each of those offsets in the committed `.frx` gives this:

| Declared offset | Declared length at it | Real gap to the next declared offset |
|---|---|---|
| `0x0000` | 112 | 116 |
| `0x0074` | 112 | 116 |
| `0x00e8` | 7489 | 7493 |
| `0x1e2d` | 7903 | 7907 |
| `0x3d10` | 6698 | 6702 |

Every gap is the declared length plus 4, in all nine gaps, and the file ends
exactly at the last item's own end. `BlobCursor::take` advances by the
declared length plus `FRX_ITEM_HEADER_LEN`, which is 12. It is wrong by 8 for
every item after the first. `corpus/vb6-code/Transparency-2D/frmTransparency.frm`
gives an independent second sample with three offsets, `0000`, `000C` and
`B2C5`, and it agrees.

## What this plan does not do

It writes no file. `inspect` writes nothing to disk and DET-06 established
that in phase 1. `ROADMAP.md` phase 4 names plan 04-04 as the owner of both
the `.frm` writer and the `.frx` writer and says they are one component. This
plan gets the blob bytes and the offset into the report so plan 04-04 has
something to write.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| file to parser | The four byte blob length comes from the file and it directly sizes a copy. It is the largest single length field this phase reads. |
| blob to blob | One blob's declared length advances the offset cursor for every later blob in the same form. |
| report to phase 4 | The `.frx` offset this plan computes is the number plan 04-04 writes into a generated `.frm`. A wrong offset there names a byte position the generated `.frx` does not hold. |
| corpus to repository | The ground truth for this plan is a committed corpus file. A test that copied bytes or a digest out of it into the repository would break the rule on derived fixtures. |
