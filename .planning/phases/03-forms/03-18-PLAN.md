## Why this gap matters more than its size

This is the third time in one phase that a value was computed, unit-tested,
and never wired to the product.

1. FRM-05: `frx::extract_blob` carried twenty passing unit tests and zero
   production call sites. Plan 03-15 closed it.
2. This gap: `handler_address` is computed, and is proved byte for byte
   against a real corpus stub, and reaches nothing.
3. Both survived a verification round that read SUMMARY files before somebody
   traced the product surface.

**A unit test on a value that nothing reads proves the function, not the
feature.** That sentence is the reason task 1 carries an end to end test and
not another unit test. Read `crates/deform6/tests/blobs.rs` before you write
that test. Plan 03-15 wrote it for exactly this reason, and its discipline is
the pattern to copy:

- It reaches the code only through the public `deform6::inspect` entry point,
  never through the inner function.
- Its module doc comment states plainly why it must not call the inner
  function.
- Its author removed the wiring on purpose, watched all four tests fail with
  "found 0", restored it, and recorded that evidence in the SUMMARY.

If the new test would still pass with the address dropped from
`EventReport`, it is the wrong test. Task 1 tells you to prove that it fails.

## What this session measured before the plan was written

**Treat every number below as a lead, not as a fact. Take each measurement
again and write your own numbers in the SUMMARY.**

Every sweep below runs the built `deform6 inspect` over all 44 corpus
executables and reads only the `Forms` section of the output.

**Walk the corpus with a null delimited loop.** Nine corpus paths hold a
space. A loop that splits on whitespace drops those nine programs and reports
a clean number over the 35 that remain. This session made that exact mistake
first, and it is the failure `AGENTS.md` names: a search for some names is
not a search for all of them. Use:

    while IFS= read -r -d '' f; do ...; done < <(find corpus -type f -iname '*.exe' -print0)

**The event slot facts.** Over 44 programs, `inspect` exits 0 on all 44 and
prints 686 control lines. 679 of them carry at least one event slot line and
7 carry none. The total is 12468 slot lines, of which 396 are bound and the
rest are unbound. No run anywhere in the sweep prints an unreadable pointer
defect, which suggests every one of the 396 bound slots decodes to a real
handler address today. Measure that count yourself; it is the number task 1's
test asserts against.

**The FRM-03 property facts.** The same sweep prints 683 lines that report a

## FRM-03's checkbox: what this session found

The planning brief asked for a finding either way, not a guess. Here is the
finding, with the measurement behind it.

`REQUIREMENTS.md` FRM-03 reads: "The tool recovers the property values of
every control, and of the form itself." It is currently `[x]`.

**The measurement does not support that sentence.** Over all 44 corpus
programs the tool prints 122 named property values and 683 records that say
present, byte offset given, opcode number given, not decoded. That is 122 of
805 property records, and five distinct property names out of the 198
`(control type, property name)` pairs the corpus `.frm` files actually set.

This is not a defect and nothing in this plan fixes it. It is the designed
consequence of decision D-01: the opcode table is never committed, the
built-in subset is small on purpose, and every property outside that subset
reports honestly. D-01 predicted it in writing: "roughly 158 of the 198 pairs
stay open after plan 03-02."

So the code is correct and the checkbox is wrong. Task 3 returns FRM-03 to
`[ ]` after the executor re-takes the measurement. Task 3 changes no
requirement wording. It changes one checkbox to match what the code supports.

Take the measurement again before you change the box. If your own numbers
disagree with these, write yours in the SUMMARY, say so plainly, and decide
from yours.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| file to address | A handler address is arithmetic over a signed relative value the file supplies. A hostile file chooses that value. |
| address to reader | A printed address is a claim about where code lives. A wrong address printed with confidence is worse than no address. |
| report to consumer | Phase 4 reads `ControlReport` to write a project and a confidence report. A field that carries a placeholder becomes a written claim. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-93 | Tampering | A hostile `rel32` in an event stub drives the handler address | high | mitigate | No new arithmetic enters `src/`. `decode_stub` already computes the address with `checked_add` and `checked_add_signed` and gives no handler on overflow. This plan only carries the value it already produces, so the existing bound holds unchanged and the gate proves it. |
| T-03-94 | Spoofing | A placeholder address printed as if it were read from the file | high | mitigate | The field is optional and a bound slot with no decoded handler carries `None`. The printer states that the address is not decoded and prints no number. A verify command asserts that no unbound line in a live run carries an address. |
| T-03-95 | Information Disclosure | An address printed for a slot that has no handler | medium | mitigate | `EventReport::Unbound` gains no field, so the type itself makes the value unreachable for an unbound slot. The verify step greps a live run to prove it. |
| T-03-96 | Repudiation | A wired value that silently stops reaching the report again | high | mitigate | `crates/deform6/tests/events.rs` reaches the value only through `deform6::inspect`, and the executor breaks the wiring on purpose, records the failure output, and restores it. This is the third occurrence of this defect class in this phase and the test is what stops a fourth. |
| T-03-97 | Tampering | A corpus derived address committed as a test fixture | medium | mitigate | Every expected address is computed from the committed corpus files at run time. A verify command asserts the test file names neither `decode_stub` nor `StubHandler`, and the acceptance criteria bar an address literal taken from a corpus binary. |
