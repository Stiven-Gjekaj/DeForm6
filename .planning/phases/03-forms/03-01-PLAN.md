## Why this plan owns `vb/mod.rs`

`crates/deform6/src/lib.rs` states the rule in its own doc comment: "The
modules below are declared here as a set, so that two plans in one wave never
edit this file." `crates/deform6/src/vb/mod.rs` states the same rule for
plans 02-02 through 02-05.

Phase 3 follows that rule. This plan declares all eight new modules in one
commit and creates each file. Every later plan then edits only the one file
it owns. `vb/mod.rs` never becomes a merge point.

This moves plan 03-02 from wave 1 to wave 2, because 03-02 edits
`vb/opcodes.rs`, a file this plan creates. The rest of the ROADMAP wave
structure is unchanged.

    - `Tiling::finish()` gives `Ok(())` when consumed equals `l_properties_length` exactly.
    - `Tiling::finish()` gives an error when consumed is below `l_properties_length`, and the error names the byte offset where the stream still holds unaccounted bytes and the count of them.

  <action>
    Add `Tiling` to `crates/deform6/src/vb/gui.rs`. It is a small accounting
    type, not a parser. It holds the declared `l_properties_length`, the
    running count of bytes the caller has accounted for, and the file offset
    the stream starts at. `Tiling::account` takes a bare `u32` and uses
    `checked_add`. `Tiling::finish` compares the running count against the

    unsound.
