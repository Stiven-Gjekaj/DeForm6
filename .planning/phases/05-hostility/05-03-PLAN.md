<objective>
Build the fuzz crate, write the one target the roadmap names, and hide every
`cargo fuzz` call behind an xtask subcommand so nobody types one by hand.

Purpose: `AGENTS.md` states that no input may panic, ever, and that fuzzing is
part of the gate and not an extra. The lint wall already makes the bad shapes
hard to write: no unchecked indexing, no plain arithmetic on a file derived
value, no unwrap on a value that came from the file. A wall that is configured
is not a wall that holds. The fuzzer is what proves it.

and not one. Half of it is already done. The root `Cargo.toml` already carries
the workspace exclusion and the release profile already aborts on panic. Verify
both, do not add either, and pass the workspace flag to `cargo fuzz init` so
the generated crate gets a workspace table of its own.

modes, and two bounded commands with every flag stated explicitly.
</objective>

<assumption_delta_decision>
**Noun that is now primary:** the run bound. One fuzz run becomes two, and the
two take different bounds.

**Decision: add-alongside.** `-max_total_time` stays for the pull request run
and `-runs` joins it for the scheduled run. Neither is promoted over the other,
because they answer two different questions.

**The evidence.**

The pull request run's bound is already fixed. Roadmap success criterion 1
gives its literal command line, and that command names
`-max_total_time=60 -rss_limit_mb=2048`. A plan that changed it to an iteration
count would contradict a success criterion that is already agreed. A wall clock
bound is also the right shape for a pull request job, because the thing being
bounded there is how long a person waits.

The scheduled run has no criterion and is where the named risk's warning
applies. A wall clock bound is flaky on a varying CI machine, because a slow
runner covers less ground than a fast one for the same minute, and two runs of
the same job then explore different amounts of the input space. An iteration
count is machine independent: the same `-runs=N` explores the same number of
inputs everywhere. The scheduled run therefore takes `-runs=N`.

The second half of the evidence decides N. `crate::error::damaged` leaks one
short string per refusal, deliberately, and `refusal_for_defect` from plan
05-01 reaches it on the strict refusal path. The fuzzer refuses almost every
input it generates, so the leak grows once per iteration. Two consequences
follow. Leak detection must be off, because the leak is a design decision and
not a fault, and it is off through `-detect_leaks=0` on both runs. And N must
be chosen so that N multiplied by the largest message this crate can leak stays
below `-rss_limit_mb`. Task 2 measures the largest message, does the division,
and picks an N at least ten times below the bound. Both numbers go into the
SUMMARY.

**What would force a promote:** removing the leak. If `Refusal::Damaged` ever
carries an owned string instead of a leaked static one, the resident set stops
growing with the iteration count, the arithmetic that picks N disappears, and
the scheduled run is free to take whichever bound reads better. That day is not
this phase. The leak is recorded as an open finding in `.planning/WINDOWS.md`
by task 3.
</assumption_delta_decision>

| fuzzer generated bytes to both library entry points | The fuzzer builds bytes no person wrote and hands them straight to the reader and the writer. This is the most hostile input this project will ever see. |
