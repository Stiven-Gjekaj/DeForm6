<objective>
Put the fuzzer in the gate. One bounded job on every pull request, one longer
job on a schedule, and both seeded from the vendored corpus and from every
committed regression input, so the fuzzer starts from real Visual Basic 6
images and from every input that once ended the process.

Purpose: `AGENTS.md` states that fuzzing is part of the gate and not an extra.
A fuzz crate that only a developer remembers to run is an extra. A job that
runs on every pull request is the gate.

The seeding matters more than the duration. A coverage guided fuzzer that
starts from an empty corpus spends most of a sixty second budget learning that
a file begins with the two letters `MZ`. A fuzzer seeded with the 44 vendored
executables starts inside the format and spends the budget on the parts of the
reader that a real file reaches. Seeding from the regression directory as well
puts every already fixed crash at the front of the campaign, so a fix that
regresses is found by the fuzzer and not only by the replay.

Output: one workflow file with two jobs, neither of which names a fuzzer flag,
because every flag lives in the xtask subcommand plan 05-03 built.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the CI runner to the repository | A workflow runs with a token. It must read the repository and never write to it. |
| a crash artifact to version control | A crash input is bytes no person wrote. It must reach a human before it reaches a commit. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-5-16 | Repudiation | a seed step that copies nothing | high | mitigate | A campaign seeded with zero files still exits zero and still looks green. The seed step prints one count per source and fails when either is zero, which is the same shape the fetch command uses in plan 05-07 for the same reason. A single combined count would hide a zero on the regression side, which is the side a fixed crash depends on. |
| T-5-17 | Elevation of Privilege | the workflow token | medium | mitigate | The permissions block grants read access to the repository contents and nothing else, copied from `gate.yml`. No step writes to the repository and no step commits. |
| T-5-18 | Tampering | a crash input committed without review | high | mitigate | The upload step puts the artifact in front of a human and nothing in CI commits it. The validation strategy records this as the one manual verification of the phase: a human confirms an artifact holds fuzzer generated bytes only, before it enters `tests/regressions/`. |
| T-5-19 | Tampering | the pinned stable toolchain | high | mitigate | Nightly is installed as a second toolchain and every fuzz call names it with the plus form. A gate assertion in task 1 fails if this workflow ever names the pin file. |
| T-5-20 | Denial of Service | an unbounded scheduled campaign | medium | mitigate | The scheduled job takes an iteration count that plan 05-03 chose by dividing the resident set limit by the largest message the crate can leak, with a stated factor of safety. The resident set limit is passed on both runs as a second bound. |
| T-5-SC | Tampering | the two CI actions and the installed tools | medium | mitigate | The checkout action and the cache action are pinned to the same major versions `gate.yml` already uses, so this workflow adds no new action to the trust set. The fuzz subcommand is installed from the registry entry audited `OK` in `05-RESEARCH.md`. |
