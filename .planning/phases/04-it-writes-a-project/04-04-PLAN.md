<objective>
Write the form file and its resource file as one component, driven by one
cursor, so that every offset a form line names resolves inside the resource
file that was actually written.

Purpose: this is the one place in the phase where two independently correct
pieces of code produce a broken result. The resource offset is not a field in
the executable. It is a running total. A form writer that computes the offset
and a resource writer that packs the records will each look right in its own
test and will drift apart the moment a form holds two blobs. The roadmap names
this, the research names it, and Phase 3 built the cursor for exactly this
reason.

The second thing this plan settles is the difference between a form that is
empty and a form that refused. Both arrive with no controls. One is
`LockWorkStation.exe`, which really has a form with no children. The other is
the form named `Main` in `Map Editor.exe`, whose control tree walk refuses at a
named byte offset. Writing the same near empty block for both is technically
loadable and is a wrong answer that looks like a right one.

Output: a form writer, a resource writer, one cursor per form, the three
ordering rules, and the honest treatment of a form whose tree refused.
</objective>

  <behavior>
    - The writer creates one cursor per form and never shares one across two forms. A second form starts its own cursor at zero.
    - The writer calls the cursor's take function once per blob bearing property, in the exact order the form writer emits those properties, and writes the value it returns as the offset in the property line.
    - The offset is written as upper case hex padded with leading zeros to at least four digits. A five digit offset is written as five digits.
    - The records in the resource file are packed end to end with no padding and no alignment, in the same order the offsets were taken.
    - A picture record is the four byte total length, the four byte marker, the four byte payload length, then the payload bytes exactly as the executable holds them.
    - A picture property whose blob is absent writes the twelve byte empty picture record, which the corpus proves is what the IDE leaves behind when a developer removes an icon.
    - A long string record is the four byte count then the text bytes, with the count excluding the four header bytes.
    - Reading the four byte length at every offset the written form file names, in the written resource file, gives a record whose end is inside the file, and the last record ends exactly at the end of the file.
    - A form that names no blob produces no resource file at all, and the form file holds no resource reference.
    - A blob the reader marked unreadable produces no line and one report item of confidence `unrecoverable` carrying the byte offset, and it does not advance the cursor.
  </behavior>
  <action>
    Reuse the cursor. Do not copy it, do not wrap it in a second offset counter
    and do not compute an offset anywhere else in this file. The struct exists
    because Phase 3 measured the advance against eleven real gaps in two
    committed resource files, after an earlier reading that was wrong by eight
    bytes. Call the constructor once per form, before the control loop, and call
    the take function once per blob bearing property, inside the loop, at the
    exact moment that property's line is emitted.

    Bind the two outputs together in one function and one return value. The
    function gives the form file bytes and an optional resource file, and the
    two are built in the same pass. Do not expose a way for a caller to obtain
    one without the other, because a caller that could would eventually compute
    an offset to bridge the gap.
