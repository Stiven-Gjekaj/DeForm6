Add a `Report` struct and `pub fn inspect(data: &[u8]) -> Result<Report, Refusal>` to `vb/mod.rs`, and re-export both from `lib.rs` with `pub use vb::{Report, inspect};`.

`Report` holds exactly the values the locked output shape needs, plus the two Phase 4 will need and this phase can already prove: `file_len: u32`, `section_count: u16`, `runtime: Runtime`, `runtime_dll: String`, `signature: [u8; 4]`, `header_offset: Off`, `runtime_build: u16`, `project_name: String`, `title: String`, `exe_name: String`, `help_file: String`, `native: bool`, `object_count: u16`.

Two of those fields exist because of an integration gap, and the reason belongs in a doc comment on the struct. `Runtime` has one variant, so `runtime` alone cannot carry evidence: asserting it equals `Runtime::Vb6` is a tautology given `Ok`, and the sweep would then be asserting only that `inspect` returned `Ok`. ROADMAP success criterion 2 requires the sweep to observe that each of the 44 files names `MSVBVM60.DLL` and reaches the Visual Basic signature, and neither fact can be observed unless it travels out of the parse into the report. `runtime_dll` carries the import entry that matched, verbatim from the file, which plan 01-06's `runtime_of` now returns. `signature` carries the four bytes plan 01-05 read from the header window. Both are also what the command line's Runtime and Header lines print, so those two lines read the file instead of repeating a literal.

`exe_name` and `help_file` are read and carried but are not in the eight-line output shape CONTEXT.md locks. Carry them anyway: `exe_name` is what Phase 4 writes as the `.vbp` `ExeName32` key, plus the literal `.exe`, because the extension is not in the file, and plan 01-08's corpus sweep asserts that all four header strings resolve on all 44 files.

Name the two fields the sweep reads exactly `native` and `project_name`, because RESEARCH.md section 7.5's sweep sketch reads those two names.

Derive `Clone, Debug, PartialEq, Eq` on `Report`. This is not optional. RESEARCH.md section 7.2 records that a missing derive on the success side of the `Result` cost a compile cycle in the research session, because `assert_eq!` on a `Result<Report, Refusal>` needs both sides to compare.

`inspect` runs the steps in the order `STRUCTURES.md` section 12 gives, and the order is load-bearing:

Parse the PE and map the `PeReject` into a `Refusal`. Then decide the runtime with `runtime_of`, before any Visual Basic structure is read. Then reach the header with `header_region` and read `VbHeader`. Then read `ProjectInfo` from `lp_project_data`. Then read the object table head from `lp_object_table`. Then build the `Report`.

Deciding the runtime second, not fifth, is what makes the third behaviour above true. A VB5 file whose header layout differs after 0x30 must be refused by name, which is what DET-04 asks for. If the header read came first, a VB5 file with a damaged header would be reported as damaged, and the user would be told the wrong thing about their file.

Per D-10, `inspect` takes a byte slice and nothing else. It opens no file and it writes no file. The command line crate does the reading. That is also what makes the Phase 5 fuzz target the real public API rather than an internal one.

Do not add a `--json` shape, a serialiser or a second output type. CONTEXT.md's first locked decision is that machine-readable output waits for Phase 4, so that one schema is introduced once rather than two being kept in step for no gain.

Write the five behaviours above as tests in a `#[cfg(test)]` module in `vb/mod.rs`, reaching the corpus bytes with `include_bytes!` as task 1 does. The third one needs the same name-patching helper plan 01-06 used; write a small copy here rather than sharing one. RESEARCH.md's Wave 0 gaps note says to duplicate a four-line test helper on purpose, so tests can fail independently.

For the fifth behaviour, write it as a grep in the acceptance command rather than as a Rust test, because it is a property of the signature, not of a value.

Then break the covered behaviour on purpose. Move the `runtime_of` call after the `VbHeader` read, run `cargo test -p deform6 --lib`, and confirm the VB5 ordering test fails with `Refusal::Damaged` instead of `Refusal::IsVb5`. Restore it, re-run, and record the observed failure in the SUMMARY.
