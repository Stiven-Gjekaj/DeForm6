`PeImage::parse(data: &[u8]) -> Result<Self, PeReject>` calls `PeFile32::parse(data)` and maps the error into `PeReject::NotPe`, which carries the `object::Error`. `object::Error` is `Copy` and `Eq`, so `PeReject` stays `Copy`. Then two checks that are ours, not `object`'s. If `nt.file_header().machine.get(LE)` is not `object::pe::IMAGE_FILE_MACHINE_I386`, return `PeReject::NotI386`. If `nt.optional_header().magic()` is not `object::pe::IMAGE_NT_OPTIONAL_HDR32_MAGIC`, return `PeReject::NotPe32`. `image_base()` returns `u64` even on the 32-bit optional header, because the trait is shared with PE32+. Narrow it with `u32::try_from(...).unwrap_or(u32::MAX)`, never with an `as` cast, which the wall rejects.

`address_of_entry_point()` is an RVA. It is not a virtual address and it is not a file offset. Wrap it in `Rva` at the point it is read, so nothing downstream can confuse it.

  <files>crates/deform6/src/read/pe.rs</files>
  <read_first>.planning/phases/01-it-reads-the-file/RESEARCH.md sections 4.8, 5.1, 5.2, 5.3, 5.4; .planning/research/STACK.md section "Corrections found while building phase 1", item 4</read_first>
  <behavior>
    - `rva_to_off(entry_rva())` on the corpus file returns a file offset inside the file, and the byte there is 0x68.
    - In `corpus/public-domain/PassGen/PassGen.exe`, whose `.data` section declares a virtual size larger than its raw size, an RVA one byte past `min(virtual_size, size_of_raw_data)` but still below `virtual_size` resolves to nothing. This is the zero-filled tail.
    - The same RVA one byte before that boundary resolves to a file offset inside that file.
    - An RVA above every section resolves to nothing.
    - `va_to_off` on a virtual address below the image base resolves to nothing.
    - `region_at(rva)` returns a `Region` whose `file_offset(Off::new(0))` equals `rva_to_off(rva)`.
    - `region_at_va(va)` and `region_at(va.to_rva(image_base))` agree for every address that resolves.
  </behavior>
  <action>
Add `SectionInfo::mapped_len`, `PeImage::section_for`, `rva_to_off`, `va_to_off`, `region_at` and `region_at_va` to `read/pe.rs`.

`mapped_len` is `min(virtual_size, size_of_raw_data)`, always. It handles both directions the PE specification allows. When virtual size is larger the difference is the zero-filled tail and the file holds no byte for it. When raw size is larger the difference is file-alignment padding, which the loader does not map, so reading it would return bytes at an address the program never sees. On the corpus, 7 of 132 sections have a virtual size larger than the raw size, all of them `.data`, and the other 125 have the padding.

Do not add a fallback that swaps in the raw size when the virtual size is 0. No corpus section has a zero virtual size, but an old linker writes 0 there for an object file, and the fallback would let a hand-made file turn any padding into readable data. Refuse, and name the section.

`section_for(rva)` computes the distance with `checked_sub` against the section's virtual address, returns false on a borrow, and otherwise takes the first section in section-table order where the distance is strictly less than `mapped_len`. First match, because it is deterministic.

This is the single most important line in the file, and it needs a doc comment that says what it is and why. `object` offers two helpers that answer the same question and disagree with each other for an address that falls in a section's zero-filled tail: one compares the distance against the virtual size and says yes, the other compares it against the mapped length and says no. 7 of the 132 corpus sections have such a tail, so the disagreement is reachable. DeForm6 owns one predicate and calls neither of them. Write that reason in the doc comment as prose. Do not write the two helper identifiers into the source file: the acceptance criterion below greps for a call to either of them, and a name written in a comment would be indistinguishable from a call site to a reader scanning for one.

<!-- planner-discipline-allow: contains_rva, pe_file_range_at -->

For the record, the two helpers on `object`'s `ImageSectionHeader` are `contains_rva` and `pe_file_range_at`. That pair is named here in the plan so the executor knows exactly which two calls are forbidden. Neither name belongs in `crates/`.

`section_for`, `rva_to_off` and `region_at` must all route through the one predicate, so they cannot disagree.

An RVA in no section resolves to nothing and, at the call site, becomes an `UnmappedAddress` defect. Do not fall back to treating the RVA as a file offset. That fallback is the classic way a decompiler reports real bytes from the wrong place: on an image where file alignment equals section alignment the two often agree, so the bug hides until one file where they do not. Do not fall back to the PE headers region either; nothing VB writes points there.

`region_at(rva)` returns a `Region` whose `base` is the resolved file offset and whose length is the remaining mapped bytes of the section. That provenance is exactly what `object` cannot give: its own helpers return a bare slice or a pair of integers with no offset attached, so an error three levels down could not name a file offset.

`region_at_va(va)` is `va.to_rva(image_base)` followed by `region_at`. There is no other route from a virtual address to bytes, because `Va` has no conversion into `Off` and no `Add`.

For the zero-filled-tail behaviours, use the second corpus file named in the precondition, `corpus/public-domain/PassGen/PassGen.exe`, bound with `include_bytes!` beside the first. Mandelbrot cannot serve here: all three of its sections have a raw size larger than their virtual size, so it has no tail and the test would pass vacuously against it.

Within that file, do not hard-code the section index. Scan the parsed section list for the first section whose virtual size exceeds its raw size, and fail with a message saying so if none is found, so the test cannot silently degrade into nothing if the corpus changes.

Write the seven behaviours above as tests in the same `#[cfg(test)]` module.

Change it to return `size_of_raw_data` and confirm the same test fails. Restore it, re-run, and record both observed failures in the SUMMARY.

Add `imported_dlls`, `delay_loaded_dlls` and `dll_name_sites` to `read/pe.rs`, using the exact shapes in RESEARCH.md section 4.5.

`import_table()` returns a `Result<Option<ImportTable>>`. `Ok(None)` means the image has no import data directory. That is not an error, and for DeForm6 it becomes "no Visual Basic runtime" in plan 01-06, not "damaged". Return an empty list.

The descriptor iterator is fallible. `ImportDescriptorIterator::next` has an inherent `next` returning `Result<Option<_>>` and does not implement `Iterator`, so a `for` loop does not compile and the `while let Some(desc) = d.next()?` shape is the one that does.

Upper-case each name with `to_ascii_uppercase`, not `to_uppercase`. A DLL name is ASCII, and the Unicode uppercase mapping of a stray high byte could produce a longer string and a wrong comparison. The PE import directory stores the name as raw bytes with no case rule, and the Windows loader resolves a module name case-insensitively, so a linker is free to write any case and different linkers do. All 44 corpus files hold the literal upper-case ASCII name, so the folding is never exercised by the corpus. Keep it anyway: it costs one method call and the counter-example is a file nobody has yet.

`delay_loaded_dlls` has the same shape over `delay_load_import_table()`. The corpus has no delay-load directory at all, in 44 of 44. Write a doc comment saying that this list is informational only and must never decide the runtime: `object` computes the delay-load name address with a wrapping subtraction and never reads the descriptor's attributes field, and the old Visual C++ 6 delay-load format stores virtual addresses there rather than RVAs. A wrapping subtraction on a garbage address cannot panic, so the worst case is a bounds-check failure, which is a damage report. Plan 01-06 owns the rule that the delay-load table never decides.

`dll_name_sites` returns a `Vec<(Off, u32)>`: for each import descriptor, the file offset of its name and the length of that name. It reads the descriptor's name RVA and maps it through `rva_to_off`. It is not a byte search. A byte search for the runtime name could hit the same bytes in `.rsrc` or in a string table, and AGENTS.md names that class of mistake directly under "a search for some names is not a search for all of them".

This method is worth its ten lines twice over. The Phase 4 report needs a byte offset as evidence for "the runtime is MSVBVM60.DLL", and plan 01-08's refusal fixtures use it to patch a name in place at the offset the PE itself names.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the file bytes -> `object` | A third-party crate that uses `unsafe` for performance parses attacker-controlled headers. |
| the section table -> every later pointer read | Every virtual address in the VB structures resolves through this map. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-11 | Spoofing | `section_for` and overlapping sections | medium | mitigate | First match in section-table order, chosen deliberately. The Windows loader maps sections in table order so a later overlapping section wins in memory; the two disagree, and a file with overlapping sections is either damaged or built to make two parsers see different bytes. The overlap is reported as a `Defect` rather than resolved silently. Untested by construction: no corpus file overlaps. |
| T-01-12 | Spoofing | the rejected "treat the RVA as a file offset" fallback | high | mitigate | The fallback is not implemented. On an image where file alignment equals section alignment it often works and is often wrong, so the bug would hide until one file where they differ. `rva_to_off` returns nothing instead. |
| T-01-13 | Elevation of privilege | memory unsafety inside `object` | medium | transfer | `object` uses `unsafe` for performance and disclaims hostile input. `#![forbid(unsafe_code)]` in the library means every unsafe line in the process belongs to `object` or to the standard library. The mitigation is this seam plus the Phase 5 fuzz target, which enters through the public API, so a crash inside `object` is found by our fuzzer and reported upstream. |
| T-01-14 | Denial of service | `imported_dlls` and `dll_name_sites` | medium | mitigate | The fallible descriptor iterator bounds every read, and a name that does not resolve through `rva_to_off` is dropped rather than read. No allocation is sized from a field in the file. |
| T-01-15 | Tampering | `PeImage::parse` read as a validity gate | high | mitigate | A doc comment states that a successful parse validates headers only, backed by the measurement that a corpus file cut to one eighth still parses. Every read after the parse goes through `Region`, whose bounds come from the real slice length. |
</threat_model>
