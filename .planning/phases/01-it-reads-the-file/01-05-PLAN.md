<task type="auto" tdd="true">
  <name>Task 1: Reach the VB header from the entry stub, and refuse every unsampled variant</name>
  <files>crates/deform6/src/vb/header.rs</files>
  <read_first>.planning/research/STRUCTURES.md sections 1.1, 1.2, 1.3; .planning/phases/01-it-reads-the-file/RESEARCH.md section "Code Examples", subsection "Resolve the entry point and reach the VB header"</read_first>
  <behavior>
    - On the corpus file, the byte at the entry point is 0x68 and the header region's first four bytes are the ASCII `VB5!`.
    - The header region's `file_offset` at window offset 0 is a file offset inside the file, and the four bytes read from the raw file at that offset are `VB5!`.
    - With the entry byte patched in memory from 0x68 to 0x5A, the result is `Refusal::Damaged` and not a successful read. 0x5A is the opcode `STRUCTURES.md` section 1.3 names with no sample.
    - With the entry byte patched to 0x11, the result is `Refusal::Damaged`. That is the other unsampled opcode.
    - With the four signature bytes patched from `VB5!` to anything else, the result is `Refusal::Damaged`.
    - With the pushed operand patched to an address below the image base, the result is `Refusal::Damaged` and not a read of the DOS stub.
  </behavior>
  <action>
Write `vb::header::header_region(pe: &PeImage) -> Result<Region<'_>, Refusal>` in `vb/header.rs`.

Do not disassemble. Pattern-match and then validate, which is what `STRUCTURES.md` section 1.2 recommends.

Take `pe.region_at(pe.entry_rva())`. If the entry point is in no section, refuse with `Refusal::Damaged` and a static fragment saying the entry point is in no section.

Read the byte at window offset 0. If it is not 0x68, refuse with `Refusal::Damaged` and a fragment saying the entry point is not a push of an immediate. Per D-06 do not accept 0x5A and do not accept a second opcode at offset 5. `STRUCTURES.md` section 1.3 records that one prior tool accepts 0x5A and 0x11 with no sample and no explanation, and notes that 0x5A is `pop edx`, which does not fit the stated five-byte layout, so it may be dead defensive code rather than a real variant. All 44 corpus files use the documented stub. A variant with no sample is a guess with a code path, and a code path nobody can exercise is a place a hostile file can go and a test cannot follow.

Read the `u32` at window offset 1 with `va_le`, which returns a `Va`. Typing it at the read is the point: the value is a virtual address and nothing downstream may treat it as anything else.

Take `pe.region_at_va(va)`. That call is `Va::to_rva` against the image base followed by `region_at`, and it is the only route from a virtual address to bytes. An address below the image base returns nothing, so it becomes a refusal rather than a read of the DOS stub.

Compare the first four bytes of that region against the literal `VB5!` using `take`. Refuse if they differ. Note in a doc comment that this signature is present in VB5 and in VB6 alike, so it proves the file is Visual Basic and does not prove the version. The version comes from the imported runtime name in plan 01-06, which is what DET-03 requires.

Return `subregion(Off::new(0), 0x68)`, a window whose offset 0 is the `VB5!` magic and whose `base` is the header's file offset. The `VBHeader` structure is 0x68 bytes. Rebasing here is what lets a defect in task 2 name an absolute file offset with no caller threading one through.

Do not add the optional stronger check on the byte at entry+5. `STRUCTURES.md` section 1.2 calls it the strongest check but says it needs a disassembler, and recommends treating it as a confidence upgrade in the report rather than as a gate. It is not needed for DET-02 and it belongs to Phase 4's evidence, not here.

Write the six behaviours above as a `#[cfg(test)]` module in this file, with the outer `#[allow(...)]` attribute from RESEARCH.md section 2.5. Every patched case builds its bytes inside the test from a copy of the corpus file in a `Vec<u8>`. Nothing is written to disk.

To patch the entry byte, resolve the entry point through `PeImage::rva_to_off` and write at that offset. Do not search for a byte pattern. The offset comes from the file's own header, which is the same discipline `dll_name_sites` uses in plan 01-04.

Name the two opcode tests so the reason is visible in `cargo test` output, for example `an_entry_opcode_of_0x5a_is_refused_because_no_corpus_file_shows_it`.

Then break the covered behaviour on purpose. Add 0x5A to the accepted opcode set, run `cargo test -p deform6 --lib`, and confirm the 0x5A test fails. Restore it, re-run, and record the observed failure in the SUMMARY.
  </action>
  <verify>
    <automated>cargo test -p deform6 --lib && cargo fmt --all --check && cargo clippy --all-targets -- -D warnings</automated>
  </verify>
  <done>
All six behaviours pass. Only opcode 0x68 is accepted at the entry point, and the two unsampled opcodes each have a named test proving they are refused. The deliberate breakage was run and made the 0x5A test fail, and it is recorded in the SUMMARY. The gate is green.

Commit subject: `reach the VB header from the entry point stub`

<task type="auto" tdd="true">
  <name>Task 2: The VBHeader fields, and the two kinds of pointer one structure mixes</name>
  <files>crates/deform6/src/vb/header.rs</files>

  <behavior>
    - On the corpus file, `exe_name` is `Mandelbrot`, which is the `.vbp` `ExeName32` value with `.exe` removed.
    - On the corpus file, `title` is `Mandelbrot Fractal Demo`, which is the `.vbp` `Title` value.
    - On the corpus file, `help_file` is the empty string, which is the `.vbp` `HelpFile` value.
    - On the corpus file, `project_name` is `Mandelbrot_Fractal_Demo`, which is the `.vbp` `Name` value.
    - `lp_project_data` is a `Va` and it resolves through `PeImage::region_at_va` to a readable region.
    - `lp_sub_main` on the corpus file is null, which means the startup object is a form.
    - `runtime_build`, `w_form_count` and `w_external_count` are read and returned, and no test compares any of them against a literal.
    - The four string offsets satisfy `exe_name_offset < title_offset < help_file_offset <= project_name_offset`.
  </behavior>
  <action>
Add a `VbHeader` struct and `VbHeader::read(hdr: &Region) -> Result<VbHeader, Refusal>` to `vb/header.rs`, reading from the 0x68 byte window task 1 returns.

Read these fields, using the offsets and the names in `STRUCTURES.md` section 2, all confidence [C] except where noted:

`runtime_build`, a `u16` at 0x04. `lp_sub_main`, a `Va` at 0x2C, where null means the startup object is a form rather than a module. `lp_project_data`, a `Va` at 0x30, the spine of the whole file. `f_mdl_int_ctls` and `f_mdl_int_ctls2`, `u32` at 0x34 and 0x38. `w_form_count`, a `u16` at 0x44, which is the loop bound Phase 3 uses. `w_external_count`, a `u16` at 0x46. `lp_gui_table`, a `Va` at 0x4C. `lp_external_table`, a `Va` at 0x50.

Then the four string offsets. Per D-09 and `STRUCTURES.md` section 13, name them `o_project_exe_name` at 0x58, `o_project_title` at 0x5C, `o_help_file` at 0x60 and `o_project_name` at 0x64. Read each with `off_le`, so it comes back typed as an `Off`.

This is the point of non-negotiable importance, and it needs a doc comment on the struct. One structure mixes two kinds of pointer. The field at 0x30 is a virtual address. The four fields at 0x58, 0x5C, 0x60 and 0x64 are byte offsets from the start of the VBHeader. `STRUCTURES.md` section 13 records what happens when they are confused: a first attempt at the gap check treated 0x58 as a virtual address, resolved it through the section table, and read the string `MZ` out of the DOS stub, because the stored value was small enough to look like a plausible address. The value is 0x78 and the header sits at file offset 0x1760.

Make the confusion impossible by typing rather than by comment. The virtual-address fields are `Va` and can only reach bytes through `PeImage::region_at_va`. The four string offsets are `Off` and can only reach bytes through `Region::cstr` on the header window itself. `Va` has no conversion into `Off`, no `From<u32>` and no `Add`, so there is no expression that crosses the two without going through `to_rva`, which takes an image base and would be visibly wrong here.

Resolve each string with `hdr.cstr(offset, max)` against the same header window that task 1 returned, never against the file and never against the image base. Use a `max` of 0x104 for the exe-name and help-file slots and 0x104 for the others as well; `STRUCTURES.md` section 2.3 records a prior tool bounding the title at 0x28, and the corpus's largest header-relative string offset is 171, so a uniform 0x104 is inside the safe range and needs no per-field table. A `cstr` that finds no NUL inside `max` is a refusal, not a truncation.

Decode each string with `char::from(byte)`, which maps a byte to the Latin-1 code point and is the right default for a VB6 header string. Do not use `String::from_utf8_lossy`: a byte in 0x80 to 0xFF would become the replacement character and the name would be lost. The full Windows-1252 table arrives with `VbStr` in Phase 3.

Do not read the sixteen bytes at header-relative 0x68 to 0x77. RESEARCH.md section 8.5 measured them as zero in every corpus file and `STRUCTURES.md` does not name them. Do not assume the string pool always starts at 0x78 either, even though it does in all 44 files: follow the offset in the field, as the format requires. Never derive a string's length from the next offset; read to the NUL with a bound.

Write the eight behaviours above as tests. The four string values are pinned as literals on purpose: they are what the `.vbp` beside the executable declares, and RESEARCH.md's Pitfall 6 says to assert on the project name and the mode, which the `.vbp` proves, and not on a size, a section count or a build number. Do not pin `runtime_build`, the file size or the section count anywhere.

The four string assertions are also the proof that the two pointer kinds are not confused. If someone resolves 0x58 as a virtual address, the value comes back as `MZ` and the test fails with that exact string. Say so in a comment on the test.

Then break the covered behaviour on purpose. Change the exe-name resolution to go through `pe.region_at_va(Va::new(offset.get()))` instead of `hdr.cstr(offset, max)`, run `cargo test -p deform6 --lib`, and confirm the `exe_name` test fails and that the value it reports is `MZ`. Then swap the 0x58 and 0x5C reads and confirm both the `exe_name` and the `title` tests fail. Restore both, re-run, and record both observed failures and the `MZ` value in the SUMMARY.
  </action>
  <verify>
    <automated>cargo test -p deform6 --lib && cargo fmt --all --check && cargo clippy --all-targets -- -D warnings && ! grep -q 'from_utf8_lossy' crates/deform6/src/vb/header.rs</automated>
  </verify>
  <done>
All eight behaviours pass. The four header strings equal the four `.vbp` values for the corpus file. The struct's doc comment states that one structure mixes a virtual address and four header-relative offsets, and the types enforce it. The two deliberate breakages were run, the first reported `MZ`, and both are recorded in the SUMMARY. The gate is green.

Commit subject: `read the VBHeader fields and its four header relative strings`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the entry point bytes -> the header address | One `u32` read out of the file decides where the whole parse goes next. |
| the header window -> four string reads | Four `u32` values out of the file decide where four strings are read from. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-16 | Spoofing | the four header-relative string offsets | high | mitigate | The offsets are typed `Off` and resolve only inside the 0x68-byte header window through `Region::cstr`. `Va` and `Off` do not convert into one another, so an offset cannot be resolved as an address. The four corpus string assertions fail with the literal `MZ` if the mistake is made, which makes the fault loud rather than plausible. |
| T-01-17 | Denial of service | `Region::cstr` on a header with no NUL | medium | mitigate | `max` is 0x104 and mandatory. A header window with no NUL byte returns nothing, which becomes a refusal. The window itself is 0x68 bytes, so a run cannot leave the header. |
| T-01-18 | Tampering | an entry stub variant with no sample | medium | mitigate | Only opcode 0x68 is accepted. Two unsampled opcodes each have a named test proving they are refused. An accepted variant nobody can produce a file for is a code path a hostile file can reach and a test cannot follow. |
| T-01-19 | Spoofing | the pushed virtual address | high | mitigate | `region_at_va` is the only route from the address to bytes, and it goes through `Va::to_rva`, a `checked_sub` against the image base, then through the one section predicate from plan 01-04. An address below the image base or outside every section refuses. |
</threat_model>
