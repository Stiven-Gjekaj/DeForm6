<objective>
Build `vb/runtime.rs`: decide the Visual Basic version from the imported runtime
DLL name, and produce the refusals for every version this tool does not read.

Purpose: DET-03 and DET-04. Both runtimes write `VB5!`, so the signature cannot
tell the versions apart. The runtime DLL name is the discriminator the format
itself uses, four independent implementations use it, and 44 of 44 corpus files
agree.

Output: one file holding a pure classifier that needs no file, and the wiring
that turns an import directory result into a refusal.
</objective>

    - A list holding the same name in lower case, `msvbvm60.dll`, also classifies as Visual Basic 6.
    - A list holding `MSVBVM50.DLL` gives `Refusal::IsVb5`.
    - A list holding `VB40032.DLL` gives `Refusal::IsVb4`.
    - A list holding only `KERNEL32.DLL` gives `Refusal::NoVbRuntime` with `dot_net` false.
    - The same list, with the .NET flag set, gives `Refusal::NoVbRuntime` with `dot_net` true.
    - An empty import list gives `Refusal::NoVbRuntime`.
    - A list whose imports hold no VB runtime but whose delay-load list holds `MSVBVM60.DLL` gives `Refusal::NoVbRuntime`. The delay-load table never decides.
    - A list holding both `MSVBVM60.DLL` and `KERNEL32.DLL` classifies as Visual Basic 6.
  </behavior>
  <action>
Write `vb/runtime.rs` with the four name constants from RESEARCH.md section 6.1 exactly: `VB6_DLL` is `MSVBVM60.DLL`, `VB5_DLL` is `MSVBVM50.DLL`, `VB4_32_DLL` is `VB40032.DLL`, `VB4_16_DLL` is `VB40016.DLL`.

Keep `VB4_16_DLL` even though it is unreachable. RESEARCH.md section 6.5 proved why: a 16-bit VB4 program is an NE executable, not a PE one, and `PeFile32::parse` on an image whose `e_lfanew` points at `NE` returns an error, so the refusal is `NotPe` and exit code 1 and the name is never compared. The constant documents the intent and costs nothing. Per D-04, do not write a test that asserts a VB4 16-bit file reaches a Visual Basic refusal; plan 01-04 already tests that an NE image reaches `PeReject::NotPe`, which is the true behaviour.

Add a `Runtime` enum with `Vb6` and nothing else. There is no `Vb5` or `Vb4` success value, because those are refusals, not outcomes. Derive `Clone, Copy, PartialEq, Eq, Debug`.

Write the classifier as a pure function over data, not over a file:

`classify(imports: &[String], delay_loaded: &[String], dot_net: bool) -> Result<Runtime, Refusal>`

Match case-insensitively. `PeImage::imported_dlls` already upper-cases with `to_ascii_uppercase`, and this function folds again with `eq_ignore_ascii_case` so it is correct on any caller's input. Use ASCII folding, never Unicode folding: a DLL name is ASCII, and the Unicode uppercase mapping of a stray high byte could produce a longer string and a wrong comparison. RESEARCH.md section 6.2 records that all 44 corpus executables hold the literal upper-case name, so the folding is never exercised by the corpus; keep it, because it costs one method call and the counter-example is a file nobody has yet.

The rules, in order: if any import matches `VB6_DLL`, return `Runtime::Vb6`. If any import matches `VB5_DLL`, return `Refusal::IsVb5`. If any import matches `VB4_32_DLL`, return `Refusal::IsVb4`. Otherwise return `Refusal::NoVbRuntime` carrying the `dot_net` flag.

Per D-04, `IsVb4` maps to exit code 3, the same code as `IsVb5`, and code 3 means "a Visual Basic runtime that DeForm6 does not read". The sentence, which plan 01-03 attached to the variant, names the version, so the human loses nothing and a script that sorts a directory by exit code gets the right bucket.

The `delay_loaded` argument is taken and is deliberately not used in the decision. Write that in the doc comment with the reason. The corpus has no delay-load directory at all, in 44 of 44. The VB6 linker does not emit one for the runtime, because the runtime entry point is called from the entry stub itself before any user code runs. And `object`'s delay-load name resolution computes the address with a wrapping subtraction and never reads the descriptor's attributes field, while the old Visual C++ 6 delay-load format stores virtual addresses there rather than RVAs; the bit that distinguishes them is not documented in the Microsoft PE specification. So the list is read and reported as information and never given a vote. A file whose only Visual Basic runtime reference is delay-loaded is refused, and plan 01-08's message says the delay-load table was seen.

Take the parameter rather than dropping it, because that is what makes the ninth behaviour above a real test: a caller can hand this function a delay-load list holding the VB6 runtime and watch it still refuse. A function that did not take the list could not be tested for the property.

  <behavior>
    - `runtime_of` on `corpus/vb6-code/Mandelbrot/Mandelbrot.exe` returns Visual Basic 6.
    - `runtime_of` on the same file with the imported runtime name patched in memory to `MSVBVM50.DLL` gives `Refusal::IsVb5`.
    - `runtime_of` on the same file with the name patched to `VB40032.DLL` followed by a NUL gives `Refusal::IsVb4`.
    - `runtime_of` on the same file with the name patched to `KERNEL32.DLL` gives `Refusal::NoVbRuntime` with `dot_net` false.
    - `runtime_of` on the same file truncated to half its length gives `Refusal::Damaged`, not `Refusal::NoVbRuntime`.
    - `runtime_of` on a synthetic PE with no import data directory gives `Refusal::NoVbRuntime`, not `Refusal::Damaged`.
  </behavior>
  <action>
Add `runtime_of(pe: &PeImage) -> Result<Runtime, Refusal>` to `vb/runtime.rs`. It is four lines over `classify`.

Call `PeImage::imported_dlls`. The three cases it can produce are distinct and each maps to a different answer, so write them as three arms rather than as one:

An error from the import walk means the data directory RVA is unmapped or the descriptors are truncated. That is `Refusal::Damaged` with a static fragment saying the import directory is unreadable. It is exit code 4, not exit code 2. A truncated Visual Basic 6 file must not be reported as "this holds no Visual Basic runtime", because the two say different things to a person sorting a directory.

An empty list, which is what a missing import data directory produces, means `Refusal::NoVbRuntime`. That is not an error and it is not damage.

A non-empty list goes to `classify` together with `delay_loaded_dlls` and `has_clr_header`. Let a failure of the delay-load walk degrade to an empty list rather than to a refusal: the list never decides anything, so an unreadable delay-load directory must not be able to change the outcome.

Write a doc comment recording the three packed-image sub-cases from RESEARCH.md section 6.3 and the answer to each, so a later reader does not add a fallback. If a packer rewrote the entry point and the import directory, none of this holds; the honest answer is to refuse and to say which check failed, and Phase 5 adds the salvage path. RESEARCH.md section 6.7 puts it plainly: confidence in the discrimination itself is high, confidence that the import table is present is a different question, and for a file with no readable import directory DeForm6 has no second opinion in this phase and should not pretend to.

Write the six behaviours above as tests. For the four patched cases, copy the corpus file into a `Vec<u8>`, resolve the first import name site through `PeImage::dll_name_sites`, and overwrite exactly that many bytes. Assert inside the helper that the replacement is the same length as the name it replaces, so a wrong-length replacement is a loud failure rather than a corrupted image. `MSVBVM60.DLL` is 12 bytes; `VB40032.DLL` is 11, so the replacement carries its own trailing NUL and the original NUL becomes a second, harmless one.

Take the offset from `dll_name_sites`, never from a byte search. A byte search for the runtime name could hit the same bytes in the resource section or in a string table, and AGENTS.md names that class of mistake directly. Nothing is written to disk: the bytes exist for the duration of one test function.

For the "no import data directory" case, build the input inside the test rather than patching a corpus file.

Then break the covered behaviour on purpose. Map the import-walk error to `Refusal::NoVbRuntime`, run `cargo test -p deform6 --lib`, and confirm the truncated-file test fails. Then map the empty list to `Refusal::Damaged` and confirm the no-import-directory test fails. Restore both, re-run, and record both observed failures in the SUMMARY.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the import directory -> the version decision | One string out of the file decides whether the tool reads the file at all. |
| the delay-load directory -> nothing | A second, weaker source that must not be allowed to influence the decision. |
