<objective>
Build `error.rs` and `journal.rs`: `Site`, `DefectKind`, `Severity`, `Defect`,
`Error`, `Refusal`, `Mode` and `Journal`.

Purpose: AGENTS.md requires that an error names the byte offset and what the
code expected to find there. That is a product surface, not a convenience. This
plan puts the message next to the variant and puts the strict-or-salvage
decision in exactly one method, so no parse site written in this phase or in
Phase 5 has to branch on the mode.

Output: the two error files, and the full `Refusal` variant set that the locked
exit-code table needs, defined once so the numbering never moves.
</objective>

  <behavior>
    - Every `DefectKind` variant renders a message that contains the byte offset it carries, formatted as hexadecimal, and names what was expected there.
    - `DefectKind::severity` is exhaustive over the variant set, written with no wildcard arm, so adding a variant later is a compile error until its severity is decided.
    - `BadMagic`, `UnmappedAddress` on a spine pointer and `PastEndOfFile` classify as `Severity::Fatal`.
    - `ImplausibleCount` on a leaf and a section overlap classify as `Severity::Recoverable`.
    - `Defect`, `Site` and `DefectKind` each implement `serde::Serialize`, proved by binding a value of each to a generic function bounded on that trait. Do not add `serde_json` to this phase to prove it: that crate belongs to Phase 4 and RESEARCH.md's dependency set does not include it here.
    - `Refusal` values compare with `assert_eq!`, so `Refusal::IsVb5 != Refusal::NoVbRuntime { dot_net: false }`.
    - Every `Refusal` variant renders one sentence, in the present tense, with no byte dump and no path.
  </behavior>
  <action>
Write `error.rs` from the shape in STACK.md section 3. Copy the field names and the message strings; that block was designed against AGENTS.md's requirement that an error names the byte offset and what the code expected to find there.

`Site` holds `offset: u32` (an absolute file offset), `rva: Option<u32>`, `structure: &'static str` and `field: &'static str`. Derives `Clone, Debug, serde::Serialize`. The `offset` field is filled from `Region::file_offset`, which plan 01-02 built, and that is the whole reason `file_offset` exists.

`DefectKind` is a `thiserror::Error` enum with `serde::Serialize`. Start from the five variants STACK.md names: `BadMagic`, `OffsetOverflow`, `PastEndOfFile`, `ImplausibleCount`, `UnmappedAddress`. Add the ones this phase needs and no more: `SectionOverlap` for the case plan 01-04 detects at parse time, `NoNulTerminator` for a `cstr` that ran out of bounded space, and `CountMismatch` for the `wCompiledObjects` against `wTotalObjects` cross-check plan 01-07 makes. Every message names its offset in hexadecimal.

`Severity` is `Fatal` or `Recoverable` with the doc comments STACK.md gives. `Fatal` means the file is not what it claims and nothing downstream is meaningful. `Recoverable` means one item is unreadable and the rest of the graph still stands.

`Defect` holds a `Site` and a `DefectKind`, derives `Clone, Debug, serde::Serialize, thiserror::Error`, and its `#[error]` string combines the two.

`DefectKind::severity` is one `match` with an arm per variant and no wildcard. Severity is a property of the defect and it is decided in one place; a wildcard would let a new variant default silently.

`Error` is the library's internal error, from STACK.md with one correction: `Refused(Defect)`, `NotVb6(&'static str)` and `IsVb5`.

Do not add STACK.md's fourth variant, `Io { path, source }`. RESEARCH.md's Architectural Responsibility Map places all file input and output in the command line crate, and per D-10 the library takes a byte slice and never opens a file, which is also what makes the Phase 5 fuzz target the real public API. An `Io` variant in the library would be dead code carrying a `PathBuf` into a crate that has no path. Plan 01-08's shell owns the input-output error and maps it to exit code 5. Record this as a correction to STACK.md section 3 in the SUMMARY, so the next reader of that document knows which of the two is current.

`Refusal` is the public outcome type that `inspect` returns as its error. Define the full set now, per D-02, so the numbering never moves even though `--salvage` does not exist until Phase 5. The variants and the exit code each maps to are:

`NotPe` maps to 1. `NotI386` maps to 1. `NotPe32` maps to 1. Per RESEARCH.md section 4.6 all three fold to "this is not a thing this tool reads", and each gets its own sentence so the message can say which of the three it was.

`NoVbRuntime { dot_net: bool }` maps to 2. The bool exists because RESEARCH.md section 7.4 recommends adding `PeImage::has_clr_header` and using it in the message text under exit code 2, and explicitly recommends against a new variant and a new exit code. One variant, one code, a better sentence: when `dot_net` is true the message says the file is a .NET assembly rather than saying only that it holds no Visual Basic runtime.

`IsVb5` maps to 3. `IsVb4` maps to 3, per D-04. Both sentences name the version found.

`Damaged(&'static str)` maps to 4. The payload is a static sentence fragment naming what the parser expected to find, such as the entry point being in no section or the import directory being unreadable.

`Refusal` derives `Clone, Copy, PartialEq, Eq, Debug` plus `thiserror::Error`. The equality derives are not optional: plan 01-08's tests assert on the variant with `assert_eq!`, and RESEARCH.md section 7.2 records that a missing derive on the success side of the `Result` cost a compile cycle in the research session. Do not add `serde::Serialize` to `Refusal` in this phase; nothing needs it yet.

Do not put an `object::Error` inside `Refusal`. `read/pe.rs` is the only file in the crate that may name `object`, per the Architectural Responsibility Map in RESEARCH.md. Plan 01-04 keeps the `object::Error` inside its own `PeReject` type for the Phase 4 report and writes a `From<PeReject> for Refusal` that drops it. There is no value in surfacing nine different English strings from a third-party crate to a user who typed a filename.

Do not write a `Refusal::sentence` method and do not build a user message in the library. The library returns values; the shell in plan 01-08 turns them into a number and a sentence.

Re-export `Refusal` twice, so both import paths in RESEARCH.md's test sketches resolve: add `pub use crate::error::Refusal;` to `vb/mod.rs` and `pub use error::Refusal;` to `lib.rs`. These are the only two lines this task adds outside `error.rs`.

Write the behaviours above as a `#[cfg(test)]` module in `error.rs`, with the outer `#[allow(...)]` attribute from RESEARCH.md section 2.5, using `#[allow]` and never `#[expect]`.

Then break the covered behaviour on purpose. Replace the arm for `BadMagic` in `severity` with `Severity::Recoverable`, run `cargo test -p deform6 --lib`, and confirm the severity test fails. Restore it, re-run, and record the observed failure in the SUMMARY.

<task type="auto" tdd="true">
  <name>Task 2: journal.rs - one record method that applies the strict or salvage policy</name>
  <files>crates/deform6/src/journal.rs</files>
  <read_first>.planning/research/STACK.md section 3 "The choke point"</read_first>
  <behavior>
    - A `Fatal` defect returns `Err` in `Mode::Strict`.
    - A `Fatal` defect returns `Err` in `Mode::Salvage` as well. Fatal always refuses, in both modes.
    - A `Recoverable` defect returns `Err` in `Mode::Strict`.
    - A `Recoverable` defect returns `Ok(fallback)` in `Mode::Salvage`, and the returned value is the fallback that was passed in.
    - In all four cases the defect is present in the journal afterwards. A strict run that refuses still knows what it saw.
    - Two recorded defects appear in the journal in the order they were recorded.
  </behavior>
  <action>
Write `journal.rs` from the choke-point block in STACK.md section 3. Per D-10 there is one `record` method and the mode is applied there and nowhere else.

`Mode` is `Strict` or `Salvage`, deriving `Clone, Copy, PartialEq, Eq, Debug`. `Journal` holds a `mode` and a `Vec<Defect>`, both private.

`Journal::record<T>(&mut self, defect: Defect, fallback: T) -> Result<T, Error>` pushes the defect first, then reads its severity through `DefectKind::severity`, then matches on the pair of severity and mode. `Fatal` refuses in both modes. `Recoverable` refuses in `Strict` and returns the fallback in `Salvage`.

Push before the match, not inside an arm. That is what makes the fourth property true: the defect is recorded even on the path that refuses, so the failure message and the Phase 4 report come from the same value.

Add `Journal::new(mode)`, `Journal::mode()` and `Journal::defects()` returning a slice. Nothing else. Do not add a method that lets a caller read the mode and branch on it; the whole design is that no parse site does that.

Salvage is not reachable from the CLI in this phase, because `--salvage` arrives in Phase 5. The `Salvage` arm is still written and still tested here, because the choke point is the mechanism SAF-03 needs and building it later would mean threading a flag through every parse site already written. Say in the module doc comment that `Mode::Salvage` has no command-line route in Phase 1.

Write the six behaviours above as a `#[cfg(test)]` module in the same file, with the outer `#[allow(...)]` attribute from RESEARCH.md section 2.5.

Then move the push into the `Salvage` arm only and confirm the "the defect is recorded in all four cases" test fails. Restore both, re-run, and record both observed failures in the SUMMARY.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the library -> the user's terminal | An error message is the only thing the tool tells a user about a file it refused. |
| a parse site -> the strict or salvage policy | If policy were read at a parse site, a salvage-only path could be reached in strict mode. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-08 | Information disclosure | `DefectKind` and `Refusal` message strings | low | mitigate | A message names a byte offset, a structure name and a field name. It never dumps file bytes and never prints a host path the user did not supply. ASVS V7 is the applicable category. |
| T-01-09 | Repudiation | `Journal::record` | medium | mitigate | The defect is pushed before the policy match, so a run that refuses still holds the evidence. RPT-05 in Phase 4 reads the same value. Proved by the "recorded in all four cases" test. |
