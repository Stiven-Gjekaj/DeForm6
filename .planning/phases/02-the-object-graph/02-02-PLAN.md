<objective>
Turn `fObjectType` into a kind: form, standard module, class, or `Unknown`
carrying the raw value.

Purpose: OBJ-02. This is the discriminator the `.vbp` comparison in plan 02-08
joins on, and the fallback arm is what keeps a file the corpus has never seen
from being refused.

Output: `vb/classify.rs` with `ObjectKind`, `classify`, and the presence test
for the optional half of `ObjectInfo`.
</objective>

  <name>Task 1: The three values the corpus proves, and the fallback that carries everything else</name>
  <files>crates/deform6/src/vb/classify.rs</files>
  <read_first>.planning/research/STRUCTURES.md section 5.5, the whole of it including the bit ladder and the disputed presence test; .planning/phases/02-the-object-graph/RESEARCH.md, "Pattern 2: classify by exact match, fall back to Unknown, never refuse" and "Pitfall 1"</read_first>
  <behavior>
    - `classify(0x0001_8083)` gives `ObjectKind::Form`.
    - `classify(0x0001_8001)` gives `ObjectKind::Module`.
    - `classify(0x0011_8003)` gives `ObjectKind::Class`.
    - `classify(0)` and `classify(0xFFFF_FFFF)` each give `ObjectKind::Unknown` carrying the value that was passed in.
    - Every one of the seventeen values `STRUCTURES.md` section 5.5 tabulates classifies to something, and none of them panics.
    - Walking `Grayscale.exe` and classifying each object gives `Form`, `Class`, `Class`, in array order.
  </behavior>
  <action>
Write `vb/classify.rs`. Give it a public `ObjectKind` enum with `Form`, `Module`, `Class` and `Unknown(u32)`, deriving `Clone`, `Copy`, `PartialEq`, `Eq` and `Debug`, and a public `classify(f_object_type: u32) -> ObjectKind`.

Match on exactly the three values this corpus proves and route everything else to `Unknown`:

    0x0001_8001 => Module
    0x0001_8083 => Form
    0x0011_8003 => Class
    other       => Unknown(other)

Start narrow. `STRUCTURES.md` section 5.5 tabulates seventeen values from one prior tool's lookup table, and a script this phase's research ran against all 44 vendored programs found exactly three of them, 53 forms, 8 standard modules and 44 classes, 105 objects in total. The other fourteen values are cited and are not measured. A value read from a document and pre-populated into a match arm silently mis-tags a real file if the document is wrong, and lands it in `Unknown` and gets it flagged if it is left out. `[VERIFIED: local]` beats `[CITED]` for a value whose only job is to name a thing.

Put the fourteen cited values in the doc comment, as a table, with a sentence saying that none of them occurs in this corpus and that a sample is what widens the match. Do not put them in the match.

Per D-08, the fallback arm carries the raw value and never refuses. The MDIForm value is in no source found and does not occur here either, so it is the value this arm exists for. Per D-07 the arm does not guess a name from a bit pattern: `Unknown(0x1DA003)` is what the report says, not `UserControl`.

Write no wildcard-free match over a value that comes out of the file. `RESEARCH.md`'s warning signs name this exactly: an exhaustive match is right over an internal enum this crate builds, and wrong over a `u32` an attacker chose.

Write the six behaviours as a `#[cfg(test)]` module. The fifth is a loop over a literal array of the seventeen values written into the test. Build that array in the test, per `AGENTS.md`: a test builds the state it needs and does not read it out of a file the author edits. The sixth reaches `Grayscale.exe` through `include_bytes!`, walks it with `ObjectTable::walk` and classifies each object, and it is the one that ties the pure function to real bytes.

Then break the covered behaviour on purpose, twice. First swap the `Form` and `Class` values in the match and confirm the `Grayscale.exe` ordered test fails. Second, replace the fallback arm with a `Refusal` and confirm the fourth behaviour fails to compile or fails at run time; record which, because a compile failure is the stronger result and means the signature itself forbids the refusal. Restore both, re-run, and record both observed failures in the SUMMARY.
  </action>

  <behavior>

    - `agree(f_object_type, lp_private_object)` is true when the `0x2` bit and the sentinel say the same thing and false when they disagree.
    - On `Grayscale.exe` the two tests agree on all three objects.
    - A synthetic pair with the `0x2` bit set and the private-object pointer at `-1` reports a disagreement and does not pick a side.
    - The two published tests are named in the doc comment with the reason each is wrong, and neither is implemented.
  </behavior>
  <action>
Add `has_optional_info(f_object_type: u32) -> bool` returning `f_object_type & 0x2 != 0`, and a second function that takes the type value and `ObjectInfo.lpPrivateObject` and says whether the two markers agree.

`STRUCTURES.md` gap 2 records that both published presence tests are wrong against the only value table that exists. One tool tests bit `0x80`, which is set for forms only, yet a class clearly carries controls and event pointers. The other tests bit `0x01`, which is set for a standard module too. Bit `0x1` of `0x2` is the only bit that separates a module from everything else across all seventeen tabulated values, so that is the test. Write both wrong tests into the doc comment with the reason each fails, so a later reader does not reintroduce one.

Cross-check against the sentinel. `STRUCTURES.md` section 5.2 records that `lpPrivateObject` at `ObjectInfo + 0x0C` is `-1` for a standard module. A script this phase's research ran found the two markers agreeing on all 105 corpus objects, zero disagreements, and a second script this planner ran found the same eight objects with no private object and the same eight objects classified `Module`. So the disagreement path has no corpus sample and must be built synthetically.

Per the ROADMAP risk on gap 2, report a disagreement rather than picking one. Return the disagreement as a `DefectKind::CountMismatch` at `Severity::Recoverable` naming both markers, or add no defect variant and return a value the caller reports; choose one and say which in the doc comment. Do not silently prefer either marker.

Do not design the report format around "usually agrees". In this corpus it always agrees, 105 of 105. The cross-check exists because a future file might not, and the doc comment must say that plainly rather than implying the corpus exercises the branch.

Write the five behaviours as tests. The fourth one is a pure-function call with two literals and needs no file at all, which is the point: the branch that no corpus file reaches is still reachable and still tested.

Then break the covered behaviour on purpose. Change the presence test from `& 0x2` to `& 0x80` and confirm the class case of the first behaviour fails, because `0x0011_8003` has no `0x80` bit. Restore it, re-run, and record the observed failure in the SUMMARY.
