Give a modifier value carrying three flags, decoded by stripping `0x80` for Optional, then `0x40` for Array, then `0x20` for ByRef, in that order, leaving the base code. That is the order section 6.5's decoder uses.

Do not emit `ParamArray`. Section 6.5 records that its encoding has no observed sample and that the natural guess makes it indistinguishable from a plain ByRef Variant array. A grep this planner ran over every source file in the corpus found zero occurrences of the keyword anywhere, so this corpus cannot confirm or refute the guess. Emitting the wrong ByRef Variant array compiles and is wrong; emitting the modifier wrongly does not compile. Name the keyword only in a doc comment, say that the encoding is a gap and that OBJ-04 is therefore partly unreachable, and produce no variant for it.

Walk the type buffer starting at `FuncTypDesc + 0x20`, in a window taken with `subregion` and bounded, never off the end of the header window. The first byte is `0x1E` for a sub or a function and `0x00` for an event; validate it is one of the two and skip it. Then take exactly `arg_size >> 2` entries. Skip zero bytes between entries, and bound that skip: section 6.6 says padding is real and must be tolerated, and a hostile `argSize` could otherwise drive an unbounded scan for a padding zero that never arrives. When the base code is `0x13`, `0x1C` or `0x1D` the entry is followed by a 32-bit value aligned up to a four-byte boundary; read it and carry it.

`RESEARCH.md`'s second pitfall is the shift. Get `argSize >> 2` wrong and the walk still appears to succeed much of the time, because the padding tolerance absorbs a short walk. So make the closure an assertion the shipped parser keeps: if the walk does not reach exactly `arg_size >> 2` entries within the step bound, report the record unrecoverable rather than accepting a partial result. A script this planner ran found the walk closing at exactly that count in 193 of 193 records, with a largest user argument count of 13, well under the 59 that section 6.6 gives as a sanity bound.

Then split the entries. When flags bit 0 is set the last entry is the return type and the rest are arguments; when it is clear every entry is an argument. Read exactly as many name pointers from `lp_ary_arg_names` as there are argument entries. Section 6.3 states the name array is not terminated, so the count must be computed first and then exactly that many entries walked. A script this planner ran found every argument name resolving in 193 of 193 records.

Decode the property kind, and **mask with `0x03`, not with `0x07`**. Section 6.6 says the low three bits hold the property kind and, in the same paragraph, that the entry count is the whole byte shifted right by two. Those two statements overlap on bit 2, so at most one of them can be right. A script this planner ran settles it: masked with `0x07`, 75 of the 193 records read as kind `4`, which is not one of the three kinds the same paragraph lists, and every one of the 75 simply has an odd entry count. Masked with `0x03`, exactly 4 of the 193 records are properties and 189 are not. Bit 2 belongs to the count. Put that measurement in the doc comment and say that section 6.6's mask is corrected here.

The four property records are the confirmation. All four sit in the class `cCommonDialog` of `Edge_Detection.exe`: `APIReturn` and `ExtendedError` each read kind `01` with flags bit 0 set, and `CustomColor` appears twice, once as kind `01` with flags bit 0 set and once as kind `10` with flags bit 0 clear. `111`, Property Set, has no sample anywhere in this corpus. Say so and leave the arm in place.

Carry the kind; do not let it change the entry count, which is the shift of the whole byte.

Write the seven behaviours as tests. The fifth one builds a synthetic buffer of zero bytes with a non-zero `argSize`, which is the shape that makes an unbounded scan run away, and asserts the read returns rather than hangs.

The measured layout at `optionalVals`:

    0x00  u32  cb_values   the byte length of the value region
    0x04  VA   p_values    equal to optionalVals + 8 in 61 of 61 records
    0x08  ..   cb_values bytes of value records, one per Optional argument, in

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `lpFuncTypeInfo` plus `ProcCount` -> an array of descriptor addresses | A pointer and a count out of the file decide how many descriptors are read. |
| `argSize` -> a walk length | One byte out of the file decides how many type entries are read and how many argument names are dereferenced. |
| `optionalVals` and `cb_values` -> a second walk | An address and a length out of the file decide a second variable-length walk. |
| a type entry's trailing pointer -> a class name or a library path | A 32-bit value out of the file is dereferenced as a structure address. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-15 | Denial of service | the type buffer walk | high | mitigate | The walk caps its own step count and treats a non-closing walk as a failure, not a loop. A hostile `argSize` cannot drive an unbounded scan for a padding zero that never arrives. A synthetic all-zero buffer proves the bound. |
| T-02-16 | Denial of service | the default-value walk | high | mitigate | The walk is bounded by `cb_values`, which is itself bounded by the window taken with `subregion`, and it must land exactly on the end. An unknown tag stops it rather than advancing by a guessed width. |
| T-02-17 | Spoofing | `lpAryArgNames` read for the wrong count | medium | mitigate | The argument count is computed from the closed type walk before any name pointer is read, and the array is not terminated, so reading one entry too many would reach unrelated bytes. The closure check is what bounds it. |
| T-02-18 | Spoofing | a record whose `constFFFF` is not `0xFFFF` | medium | mitigate | Such a record does not have the layout this code knows. It is reported unrecoverable and no prototype is produced, so a crafted record cannot present a fabricated signature as recovered. |
| T-02-19 | Information disclosure | the trailing 32-bit value of an internal or COM type entry | medium | mitigate | It is resolved through `region_at_va` like every other address, so a value that maps nowhere produces a recoverable defect and an unnamed type rather than a read of unrelated in-image bytes. |
| T-02-20 | Repudiation | the unreachable half of OBJ-04 | medium | accept | The `ParamArray` modifier has no known encoding and no corpus sample, and six of the fifteen documented type codes have no sample either. Both are recorded in the doc comment and in the SUMMARY as gaps, and OBJ-04 is reported partly unreachable rather than claimed complete. |
</threat_model>
