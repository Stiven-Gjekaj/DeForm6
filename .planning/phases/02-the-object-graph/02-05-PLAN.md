<objective>
Explain the two counts inside `PrivateObj`, walk the event descriptor pointer
array, and report what this corpus cannot prove.

Purpose: it puts the event descriptor addresses Phase 3 needs into the object
graph, and it stops two fields whose names promise more than they deliver from
being built on. Both of the structures this plan is named for are measured
absences in this corpus, and this plan says so instead of shipping an
unexercised walk that looks like coverage.

Output: the public variable and event half of `vb/privateobj.rs`, plus the two
tests that hold the absences.
</objective>

  <name>Task 1: The public variable count, carried raw, with the measurement that refutes its name</name>
  <files>crates/deform6/src/vb/privateobj.rs</files>
  <read_first>.planning/research/STRUCTURES.md sections 6.1 and 6.4, including the paragraph headed "Record stride is not stated by GD"; .planning/phases/02-the-object-graph/RESEARCH.md, "Pitfall 3: `cntPublicVars` is not what its name says"; .planning/research/STRUCTURES.md section 11 row 8</read_first>
  <behavior>
    - On `Grayscale.exe`, `pdOpenSaveDialog` reports a public variable count of 4, while the class source beside the executable declares no public variable at all.
    - On `Artificial Life.exe`, `frmMain` reports 5 while its form source declares none, and `Organism` reports 23 while its class source declares 17.
    - The accessor that gives the count is named so that a caller cannot read it as a number of recovered variables, and its doc comment carries the two counter-examples above.
    - No function in the crate walks `lpPublicVars`, and a grep proves it.
    - The gap is reported: an object carrying a non-zero public variable count produces an entry in the object's gap list naming the count and saying that the record layout behind it is unresolved.
  </behavior>
  <action>
Do not implement a `PubVarDesc` walk. `STRUCTURES.md` section 6.4 states that the record stride is not given by the one source, and gap 8 records it as unresolved. `RESEARCH.md` went further: it tried the four candidate fixed strides and the type-code-conditional stride the source's figure implies, and none produced a clean, fully resolving walk on any of the arrays it tried. That is not "not yet implemented". It is a hypothesis the corpus refutes, and writing a walk against a refuted hypothesis produces variable names that do not appear in the source file next to the binary.

Per D-14, carry `cnt_public_vars` and claim nothing about it. Name the accessor after the field, not after what the field is supposed to mean: it gives the count the structure holds, and that count is not a number of declared public variables. The doc comment carries the three counter-examples that prove it, all measured against source files in this repository:

- `pdOpenSaveDialog.cls`, present in 15 of the 44 vendored programs, declares no `Public` variable, only a `Public Enum`, and every binary reports 4 for it.
- `frmMain.frm` in `Artificial-life` declares no `Public` anything and reports 5, while carrying 10 top-level named controls.
- `Organism.cls` in `Artificial-life` declares 17 real public variables, some on comma-joined lines, and reports 23.

Say in the same comment that this is the same shape as the object table's compiled count, which turned out to be a rounded capacity rather than a count, and that the resolution path is a controlled compile-and-diff experiment, not more reading.

Add the count to a per-object gap list, so the number reaches the report as an open question rather than as an answer. Plan 02-10 prints the list. A person reading the report is told that the file holds a count of 4 there, that DeForm6 does not know what it counts, and that no variable name was recovered from it.

Write the five behaviours as tests. The first two compare a binary count against a source file this repository holds, so the counter-example is a measurement and not an assertion in a comment. Read the source with `include_bytes!` and count the declarations in the test, per `AGENTS.md`: build the state the test needs inside the test.

Then break the covered behaviour on purpose. Rename the accessor to something that reads as a count of recovered variables and add a doc line claiming it enumerates them, then confirm that no test fails. That is the finding: a name and a claim are not covered by any test. Write the covering test, which asserts the accessor's own doc comment is not the mechanism, by asserting the gap list is non-empty exactly when the count is non-zero, then re-break by making the gap list empty and confirm it fails. Restore, re-run, and record both the no-failure observation and the added test in the SUMMARY.
  </action>

<task type="auto" tdd="true">
  <name>Task 2: The event descriptor addresses, and the test that fires when the first sample arrives</name>
  <files>crates/deform6/src/vb/privateobj.rs</files>
  <read_first>.planning/research/STRUCTURES.md section 6.4, the `EventDesc` paragraphs, and section 6.2, the asymmetry note; .planning/research/STRUCTURES.md section 11 row 9</read_first>
  <behavior>
    - A public function gives, for one object, the list of event descriptor addresses, of length `cnt_events`, read from the pointer array at `lp_events_type_info`.
    - On every object of the three vendored programs the module reads, that list is empty, because every one of them reports an event count of 0.
    - A test walks every object of those programs and fails with a message naming the file and the object if any of them reports a non-zero event count. Its name says that no corpus program carries an event descriptor.
    - A synthetic object with an event count of 3 and a pointer array of three addresses gives those three addresses, so the walk is exercised by something.
    - A synthetic object with an event count of 3 and a null pointer array gives an empty list and reads no bytes at address zero.
    - No function in this crate produces an event name.
  </behavior>
  <action>
Add the event descriptor array walk and stop there.

`STRUCTURES.md` section 6.2 records the asymmetry: `lpEventsTypeInfo` is an array of **pointers**, of length `cnt_events`, while `lpPublicVars` is an array of inline records. This plan walks the pointer array, which needs no stride and no record layout, and it produces addresses.

It does not decode a descriptor. Section 6.4 records that an event descriptor has the same layout as a `FuncTypDesc`, so the decoder is the one plan 02-04 writes, and Phase 3 calls it on these addresses. Two plans in this wave must not depend on each other, and a second copy of that decoder in this file would drift from the first. Say both reasons in the doc comment.

Check the array pointer before the loop and bound `cnt_events * 4` with a checked multiply, exactly as plan 02-03 does for the name array. The null-pointer-with-non-zero-count shape is the one that dereferences address zero, and it is the shape that plan 02-03 found is real and common for the other array.

**This corpus carries no event descriptor at all.** A script this planner ran over all 44 vendored programs read `cnt_events` from every object that has a private object, 97 of them, and found 0 in 97 of 97. The other 8 objects are standard modules and have no private object. So the array is empty everywhere and the walk is exercised only by the synthetic fixtures in this task. Put that number in the doc comment and say plainly that the walk has no real sample.

Write the third behaviour as the instrument, not as a decoration. It asserts the count is zero everywhere and its failure message says that a program carrying an event descriptor has entered the corpus and that the decode path now needs a real test. A test that can only pass is worthless; this one fails the day the corpus grows, which is exactly when somebody needs to be told.

Per D-09 produce no event name. Section 6.4 records that the name strings are present in the file with no pointer to them, and that recovering one means scanning the run of strings after the last procedure name and matching by position. That is a heuristic, it belongs to Phase 3, and nothing in this phase may smuggle it in. Do not add a name field, do not add an inferred marker, and do not add a scan. Say in the doc comment that gap 9 stays open and unreached.

Write the six behaviours as tests. The fourth and fifth build a synthetic image, because no corpus file exercises either path.

Then break the covered behaviour on purpose, twice. First move the array pointer check inside the loop and confirm the fifth behaviour fails. Second, change the array element width from four bytes to two and confirm the fourth behaviour fails. Restore both, re-run, and record both observed failures in the SUMMARY.
  </action>

The two deliberate breakages were run and each made the matching test fail, and both are recorded in the SUMMARY. The three gate commands and both proof scripts exit 0.
