  <action>
Fix finding 3 first, because everything else in this plan depends on a defect reaching a caller.

Finding 3 records that `inspect` collects defects and drops them, because `Report` derives an equality trait and `Defect` does not, so a defect field could not be added without breaking the derive. `Site`, `DefectKind` and `Defect` all hold plain data: numbers and static text. Derive the equality traits on all three. That keeps the phase 1 test that compares a whole result, and it lets `Report` carry a list of defects.

Do not solve it the other way. Removing the equality trait from `Report` would break the phase 1 test that compares a result of a report against a refusal, and that test is what proves the two sides of the result are comparable at all.

Mark finding 3 fixed in `WINDOWS.md` in the documentation commit, not in the code commit, per the commit rules.

Then extend `Report`. Add the object graph, the external imports and the components, and the defects. Keep every existing field and keep its name: plan 01-08's corpus sweep and the command line both read them, and renaming one touches three crates.

Extend `inspect` to compose. It already reaches the object table head; now it walks the object array, classifies each object, resolves the procedure names, reads the type descriptors, and reads the two external tables. Each step is reached only through the address the step before it read, and each step's recoverable defects are collected into one list rather than dropped.

One recoverable failure must not lose the rest. An object whose name does not resolve keeps its other fields; an object whose type descriptor array does not resolve keeps its procedure names; a program whose component table does not resolve keeps its objects. Only a failure on the spine, which is the header, the project info and the object table head, is a refusal, and that is unchanged from phase 1.

Write a doc comment on the new fields saying which requirement each one serves, so a reader can find the answer to "why is this here" without opening the roadmap.

Write the six behaviours as tests in the module's existing test module, reaching the corpus through the inclusion macro. The sixth is a grep in the acceptance command, not a Rust test, because it is a property of the source text.

Then break the covered behaviour on purpose, twice. First, drop the defect list from the composition so it goes back to being collected and discarded, and confirm the first behaviour fails; that is finding 3 reproduced and then fixed. Second, make an unresolved type descriptor array a refusal, and confirm the fifth behaviour fails. Restore both, re-run, and record both observed failures in the SUMMARY.
  </action>

  </verify>
  <done>
