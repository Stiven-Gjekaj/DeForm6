  <behavior>
    - On `Mandelbrot.exe` the table holds one entry, it is external, and it gives the library `gdi32` and the export `SetPixelV`.
    - On `Grayscale.exe` the table holds nine entries, eight of them external, and the eight give `StretchDIBits`, `GetDIBits`, `SetStretchBltMode`, `GetObjectA` from `gdi32`, `lstrlenW` from `kernel32`, and `CommDlgExtendedError`, `GetSaveFileNameW`, `GetOpenFileNameW` from `comdlg32`, in table order.
    - On `LockWorkStation.exe` the table holds zero entries and the walk gives an empty list without refusing.
    - On `VB_Scanner_Support.exe` one library name is `EZTW32.dll`, carrying the extension, while another is `kernel32`, carrying none, and both are given verbatim.
    - An entry whose type is neither 6 nor 7 is skipped like an internal entry and produces a recoverable defect naming the value and the offset.
    - An entry whose descriptor address is in no section produces a recoverable defect and the other entries still resolve.
  </behavior>
  <action>
Add the `Declare` import table walk to `vb/project.rs`.

Open the section with a doc comment that says there are two unrelated tables in this format and both are called external. One is reached from `ProjectInfo + 0x234` with the count at `+0x238` and holds the `Declare` imports; the other is reached from the Visual Basic header at `+0x50` with the count at `+0x46` and holds the referenced components. `STRUCTURES.md` section 7 opens with the same warning. Task 3 adds the second one to this file, so the warning has to be here.

Resolve `lp_external_table`, then walk `dw_external_count` entries of eight bytes each. Take each entry as its own eight-byte `subregion`, at a base computed with a checked multiply and `Off::checked_add`. Read `dw_entry_type`, a `u32` at `0x00`, and `lp_import_descriptor`, a `Va` at `0x04`.

Bound `dw_external_count` before the loop. It is a `u32` straight out of the file. Record a `DefectKind::ImplausibleCount` at `Severity::Recoverable` when eight times the count cannot fit in the real length of the file, and clamp. The largest count measured in this corpus is 9, and the whole corpus holds 249 entries.

Process an entry only when `dw_entry_type` is 7. Type 6 is resolved inside the runtime and its descriptor points at a different shape entirely: a pair of addresses whose first four words one source reports as identical across every Visual Basic application. Dereferencing a type 6 entry as if it named a library would read unrelated in-image bytes and present them as a library and an export name. A script this planner ran found 29 of the 249 entries in this corpus are type 6, so this is a path every third program takes, not an edge case. Skip them silently: a type 6 entry is normal and is not a defect.

An entry whose type is neither 6 nor 7 is a different matter. No source describes one, so skip it and record a recoverable defect naming the value, so the report says a value nobody has documented was found at that offset.

For a type 7 entry, take the descriptor as a `subregion` of eight bytes and read `lp_dll_name` at `0x00` and `lp_api_name` at `0x04`, both virtual addresses. Resolve each with `region_at_va` and `cstr` and Latin-1 decoding, the same rule the project name uses. Do not read the third word one source mentions: it is runtime scratch, a module handle and a resolved address, and it holds nothing after loading.

Give the library name verbatim. A script this planner ran found both `comdlg32` and `comdlg32.dll` in the corpus, and `EZTW32.dll`, `winmm.dll` and `oleaut32.dll` all carrying the extension while `gdi32`, `kernel32` and `user32` do not. The extension is part of what the author wrote in the source, so normalising it would change what the recovered declaration says. Say that in the doc comment and add no normalisation.

Write the six behaviours as a `#[cfg(test)]` module reaching the four programs through `include_bytes!`. Compare the second behaviour against an ordered literal list of eight pairs, so a walk that reorders or drops one fails with both lists printed. Do not name the standard library's file system or path types anywhere in this file.

Then break the covered behaviour on purpose, twice. First process every entry regardless of its type, and confirm the `Grayscale.exe` ordered list fails because the ninth entry adds a pair. Second, change the entry stride from eight bytes to four, and confirm the same test fails. Restore both, re-run, and record both observed failures in the SUMMARY.
  </action>

  </verify>
  <done>

Library names are verbatim and one test proves that two entries in the corpus differ only by the extension. The two deliberate breakages were run and each made the ordered list fail, and both are recorded in the SUMMARY.

Add the reconstruction rules. This task is mostly about what the type refuses to say.

`STRUCTURES.md` section 7.2 names exactly what survives, the library name and the export name, and exactly what does not:

- The Visual Basic level procedure name. A source that said `Declare Function FindWindow Lib "user32" Alias "FindWindowA"` leaves only `FindWindowA` in the file. One prior tool works around this with a bundled 800 kilobyte file of known declarations and a retry that strips a trailing wide or narrow suffix. `AGENTS.md` calls that a database and not recovery, and its Measurement section says to give the number that can be proved and not to copy the habit of a tool that advertises a percentage with no evidence. Do not ship such a table. Per D-07 the export name is what is emitted and the difference is marked.
- The argument names and types. Not stored anywhere.
- Whether the declaration was public or private, and which module held it. One prior tool's own comment records that the executable does not keep it.

Model all three as markers on the recovered declaration rather than as absent fields, so a caller that prints one is forced to print the marker with it. A missing field that is simply not there gets forgotten; a marker that has to be handled does not. Plan 02-10 prints them as a comment beside the declaration, which is what section 7.2 recommends.

Add the ordinal path. Section 7.2's rule: if the name string begins with a hash and the rest parses as a decimal integer, emit an ordinal alias; otherwise emit the name. Gap 10 records that no source confirms this and no sample was ever inspected. A grep this planner ran over the corpus found no ordinal alias in any source file and none in any binary, so this corpus cannot confirm or refute it either. Per D-09 the ordinal path carries an inferred marker and the doc comment says the encoding has no sample anywhere.

Write the six behaviours as tests. The fourth and fifth are pure string cases and need no file, which is the point: the branch no corpus file reaches is still reachable and still tested, and the fifth is the one that stops a lazy parse from turning `#12a` into ordinal 12.

Then break the covered behaviour on purpose. Make the ordinal parse accept a trailing non-digit, run the tests, and confirm the fifth behaviour fails. Restore it, re-run, and record the observed failure in the SUMMARY.

  <files>crates/deform6/src/vb/project.rs</files>

  <behavior>
    - On `Server.exe` the component table holds one entry giving the file name `MSWINSCK.OCX`, the library name `MSWinsockLib.Winsock` and the component name `Winsock`.
    - On `Mandelbrot.exe` and `Grayscale.exe` the component count is zero and the walk gives an empty list.
    - The next entry starts at the current entry plus its own declared length, and an entry whose declared length is zero stops the walk with a recoverable defect rather than looping.
    - Every offset inside an entry is taken relative to the start of that entry and not relative to the table, and a test proves it by reading a second entry from a synthetic two-entry table.
    - A declared length that runs past the end of the file stops the walk with a recoverable defect.
  </behavior>
  <action>
Add the component table walk to the same file, under the doc comment task 1 wrote about the two tables.

Reach it from the Visual Basic header, not from the project info: `VbHeader.lp_external_table` at header offset `0x50` with `VbHeader.w_external_count` at `0x46`. Both are already read by plan 01-05 and neither has a caller yet. Take them as parameters rather than re-reading the header.

Entries are variable length and self-describing. `StructLength` at entry offset `0x00` gives the length of this entry, and the next entry starts at this entry plus that length. **All sub-offsets are relative to the start of the entry**, not to the table. Read three: `FileNameOffset` at `0x28`, `SourceOffset` at `0x2C` and `NameOffset` at `0x30`, each an offset from the entry start to a terminated string. Read `GUIDoffset` at `0x1C` and `GUIDlength` at `0x20` as well and carry them; a length of `-1` means there is no binary identifier at `oUuid` and a length of 72 means the textual identifier is 36 wide characters.

Bound the walk. A declared length of zero would make the cursor stand still and the loop run for the whole count, so treat it as a defect and stop. A declared length that carries the cursor past the region is a defect and stops. Section 7.3 marks the whole structure at low confidence and five of its thirteen fields are unknown, so a bound that the file cannot move is the only thing holding this walk together.

Say what the sample is. A script this planner ran over all 44 vendored programs found three component entries in total, in 3 programs, and all three name the same control: file `MSWINSCK.OCX`, library `MSWinsockLib.Winsock`, component `Winsock`, with a declared entry length of 368. So this walk has exactly one distinct sample. Put that number in the doc comment. One sample proves the three string offsets resolve; it does not prove the walk advances correctly, which is why the fourth behaviour builds a synthetic two-entry table.

Say what the table is for, so the next phase does not re-derive it: the library name string is the key that links a form's external control to its identifier, and this table is what produces the component lines of the project file in Phase 4.

Write the five behaviours as tests. The third, fourth and fifth are synthetic, because a corpus with one entry per file cannot exercise a second entry, a zero length or an overrun. Build the images with the synthetic builder `vb/header.rs`'s test module already holds, rather than patching a corpus file: both corpus files place the import directory where the address equals the file offset, and a fixture built from one of them can pass under that identity while proving nothing.

Then break the covered behaviour on purpose, twice. First read the three string offsets relative to the table rather than relative to the entry, and confirm the fourth behaviour fails on the second entry while the first still passes, which is exactly the shape that a one-entry corpus would have hidden. Second, remove the zero-length guard and confirm the third behaviour fails or times out; if it hangs rather than failing, say so, because a hang is the finding. Restore both, re-run, and record both observed failures in the SUMMARY.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `dwExternalCount` -> a loop bound | A `u32` out of the file decides how many eight-byte entries are read. |
| `dwEntryType` -> which shape a descriptor is read as | A `u32` out of the file decides whether an address is dereferenced as a library and export name pair. |
| `StructLength` -> the cursor of a variable-length walk | A `u32` out of the file decides where the next entry starts. |
| a library name and an export name -> printed text | Two addresses out of the file become a declaration a user reads and, in Phase 4, source written to disk. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-25 | Information disclosure | a type 6 entry dereferenced as an external import | high | mitigate | Only type 7 entries are dereferenced. A type 6 descriptor points at a different shape, and reading it as a name pair would present unrelated in-image bytes as a library and an export name. 29 of the 249 entries in this corpus are type 6, so the guard is exercised by real files. |
| T-02-26 | Denial of service | `dwExternalCount` as a loop bound | high | mitigate | Bounded against the real length of the file before the loop, with `ImplausibleCount` at `Recoverable` and a clamp. Nothing is allocated from the raw field. |
