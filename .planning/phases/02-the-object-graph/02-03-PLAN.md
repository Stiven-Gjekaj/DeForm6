  <name>Task 1: ObjectInfo and PrivateObj, with the module sentinel as a case and not an error</name>
  <files>crates/deform6/src/vb/privateobj.rs</files>
  <read_first>.planning/research/STRUCTURES.md sections 5.2, 6.1 and 6.2; crates/deform6/src/vb/project.rs, `ObjectTableHead::read`, for the window-before-fields shape to copy</read_first>
  <behavior>
    - On `Grayscale.exe`, `ObjectInfo::read` resolves for all three objects and each carries a `lp_private_object` that is neither `0` nor `-1`.
    - On `Map Editor.exe`, the two objects that classify `Module` each carry `lp_private_object` equal to `-1`, and reading them gives `PrivateObj::Absent` rather than a refusal.
    - On `Grayscale.exe`, `PrivateObj::read` for `FastDrawing` gives a non-null `lp_func_type_info` and carries `cnt_public_vars` and `cnt_events`.
    - `cnt_events` is `0` for every object in all three vendored programs the module reads.
    - With `lp_object_info` patched to an address in no section the read gives `Refusal::Damaged`.
    - With the file truncated so the `0x38`-byte `ObjectInfo` window runs past the end the read gives `Refusal::Damaged`.

  <action>
Write the two structure reads into `vb/privateobj.rs`.

`ObjectInfo::read(pe, lp_object_info) -> Result<ObjectInfo, Refusal>`. Resolve the address, then take a `subregion` of exactly `0x38` bytes, which is the size `STRUCTURES.md` section 5.2 gives, before any field is read. Read two fields and no more: `w_object_index`, a `u16` at `0x02`, and `lp_private_object`, at `0x0C`. Read `lp_private_object` as a raw `u32` and not as a `Va`, because `-1` is a sentinel and not an address, and a `Va` that carries `0xFFFFFFFF` invites a caller to resolve it.

Leave the rest of `ObjectInfo` unread. `wMethodCount` and `lpMethods` point into code in a native build and are Phase 3 and later work; `lpProjectData` is in-memory scratch. Say so in the doc comment so a later reader does not extend this function.

`PrivateObj::read(pe, lp_private_object) -> Result<PrivateObj, Refusal>` where the return carries either the read structure or an explicit absence. Model the absence in the type. The sentinel `0xFFFFFFFF`, and a plain `0`, both mean the object has no private object, which `STRUCTURES.md` section 5.2 records for a standard module. That is a case, not an error: refusing here would lose every module in the corpus. Give the type two states, one holding the fields and one holding nothing, and give the doc comment the reason.

When the pointer is a real address, take a `subregion` of exactly `0x40` bytes, which is the size section 6.1 gives, then read four fields: `cnt_public_vars`, a `u16` at `0x10`; `cnt_events`, a `u16` at `0x12`; `lp_func_type_info`, a `Va` at `0x18`; `lp_events_type_info`, a `Va` at `0x24`. Read `lp_public_vars`, a `Va` at `0x20`, as well, so plan 02-05 has it.

Carry `cnt_public_vars` and claim nothing about it. Per D-14 it does not count source-level public variable declarations: a class in this corpus that declares none reports 4, and a form that declares none reports 5. Put that measurement in the field's doc comment now, so nothing downstream is written against the name. Plan 02-05 owns the explanation.

The count for `lp_func_type_info` is not in this structure. `STRUCTURES.md` section 6.1 states it plainly: the count comes from `Object.ProcCount` at `Object + 0x1C`, which plan 02-01 already carries and already bounded against the real size of the file. Say that in the doc comment on `lp_func_type_info` and do not re-derive a count here.

Write the six behaviours as a `#[cfg(test)]` module, reaching `Grayscale.exe` and `Map Editor.exe` through `include_bytes!`. Do not name the standard library's file system or path types anywhere in this file, in code or in a comment.

Then break the covered behaviour on purpose. Read `lp_private_object` from `0x08` instead of `0x0C`, run the tests, and confirm the second behaviour fails because the two modules no longer report the sentinel. Restore it, re-run, and record the observed failure in the SUMMARY. If the breakage produces no failure, that is the finding: write the missing test and re-break.
  </action>

  </verify>
  <done>

<task type="auto" tdd="true">
  <name>Task 2: A null entry is a private procedure, and a null array is a different thing entirely</name>
  <files>crates/deform6/src/vb/privateobj.rs</files>
  <read_first>.planning/research/STRUCTURES.md section 5.1, the `lpProcNamesArray` row, and section 6.2; .planning/phases/02-the-object-graph/RESEARCH.md, "Anti-Patterns to Avoid", the first bullet</read_first>
  <behavior>
    - On `Grayscale.exe`, `FastDrawing` gives eight procedure slots of which four are `Public` named `GetImageWidth`, `GetImageHeight`, `GetImageData2D` and `SetImageData2D`, at indices 4 to 7, and four are `Private`.
    - On `Grayscale.exe`, `pdOpenSaveDialog` gives six slots and every one is `Private`, because the two procedures its source declares are `Friend` and only `Public` survives here.
    - On `Mandelbrot.exe`, `frmFractal` gives nine slots and every one of the nine is `Private`.
    - On `Map Editor.exe`, both standard modules give the absent-array state carrying their `proc_count`, 1 and 7, and give no slot list at all.
    - The absent-array state and a list of nine `Private` slots are different values and a test compares them and finds them different.
    - A synthetic object whose `lp_proc_names_array` is null and whose `proc_count` is 7 produces the absent-array state and reads no bytes at address zero.
  </behavior>
  <action>
Add the name walk. Model the two null cases as two different things in the type system, because they are two different facts and the whole of OBJ-03's honesty rests on the difference.

Give a `Procedure` enum with `Public(String)` and `Private`, deriving `Clone`, `Debug`, `PartialEq` and `Eq`. Give a second enum for the per-object result with two states: one holding a `Vec<Procedure>` of length `proc_count`, and one holding only `proc_count` and meaning that the object carries no name array. Name the second state so a reader cannot mistake it for an empty list.

The walk checks the array pointer **before** the loop. `RESEARCH.md` names this as the first anti-pattern of the phase: code that only tests `entry == 0` inside a loop over `proc_count` either skips the body by accident or, worse, dereferences address zero when it is written to check the pointer first and then trust `proc_count`. Check the pointer, return the absent state, and never enter the loop.

Per D-13 the absent case is measured and common, not theoretical. A script this planner ran over all 44 vendored programs found `lpProcNamesArray == 0` in exactly 8 of 105 objects, and those eight are exactly the eight objects whose `fObjectType` is `0x0001_8001`, the standard-module value, with `ProcCount` from 1 to 7. Put those numbers in the doc comment on the absent state. Per D-10 that is the `.bas` cap, stated here in the type, before any ratio is pinned.

Do not classify inside this file. The absent state is decided by the null pointer, not by asking `classify` whether the object is a module. The two facts agree in this corpus and keeping them independent is what lets plan 02-08 check that they agree.

When the pointer is real, take a window of `proc_count * 4` bytes with a checked multiply, then read `proc_count` virtual addresses out of it. A null entry gives `Procedure::Private`. A non-null entry resolves through `region_at_va` and `cstr` with a `0x104` limit and Latin-1 decoding, and gives `Procedure::Public`. An entry that resolves nowhere gives `Procedure::Private` plus a `DefectKind::UnmappedAddress` at `Severity::Recoverable`, so an unreadable name is reported and is never presented as a recovered name.

Per OBJ-06 nothing here invents a name. There is no index number, no placeholder and no name derived from a vtable offset. A private procedure is `Private` and carries nothing.

Write the six behaviours as tests. The third one is the correction this plan carries: `CONTEXT.md` records the worked example "Mandelbrot 9 of 9", and a script this planner ran gives 0 named of 9 slots, because every procedure in `Mandelbrot.frm` is declared `Private`. Assert the measured value, 9 slots and 9 `Private`, and record the disagreement in the SUMMARY as a defect found in the plan's inherited numbers.

The sixth behaviour needs a synthetic object rather than a corpus file, because a corpus module already has a null pointer and would pass under an implementation that happened to skip the loop for another reason. Build an `Object` value directly in the test with a null array pointer and a non-zero count.

Then break the covered behaviour on purpose, twice. First move the pointer check inside the loop so it becomes an entry check only, and confirm the fourth or sixth behaviour fails. Second, make a null entry return an error instead of `Private`, and confirm the third behaviour fails. Restore both, re-run, and record both observed failures in the SUMMARY.
  </action>
  <verify>
    <automated>cargo test -p deform6 --lib vb::privateobj && cargo fmt --all --check && cargo clippy --all-targets -- -D warnings</automated>
  </verify>
  <done>
All six behaviours pass. A null entry and a null array pointer are two different values of two different shapes. The pointer is checked before the loop. The `Mandelbrot.exe` measurement is asserted at 9 slots and 9 private, and the disagreement with the inherited worked example is recorded in the SUMMARY. The two deliberate breakages were run and each made the matching test fail, and both are recorded.

Commit subject: `Report a private procedure as private and a missing array as missing`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `lpObjectInfo` and `lpPrivateObject` -> two structure windows | Two addresses out of the file decide where 56 and 64 bytes are read from. |
| `lpProcNamesArray` plus `ProcCount` -> an array of addresses | A pointer and a count out of the file decide how many addresses are dereferenced. |
| a procedure name string -> printed text | An address out of the file becomes a name a user reads and, in Phase 4, an identifier written into source. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-10 | Tampering | `lpProcNamesArray` null with `ProcCount` non-zero | high | mitigate | The pointer is checked before the loop and the absent state is returned. A crafted file that reports procedures which do not exist cannot make the walk dereference address zero. This is the exact shape the standard-module measurement surfaced as a real and common case, not a theoretical one. |
| T-02-11 | Denial of service | `proc_count * 4` as a window size | high | mitigate | Checked multiply, and the window is taken with `subregion` so it is bounded by the real length of the file. Plan 02-01 already clamped `proc_count` and recorded a defect when the file cannot hold it. |
| T-02-12 | Spoofing | a name entry resolving into unrelated bytes | medium | mitigate | An entry that resolves nowhere gives `Private` plus a recoverable defect naming the offset and the address, so an unreadable name is never presented as a recovered name. |
| T-02-13 | Denial of service | the `ObjectInfo` and `PrivateObj` windows | high | mitigate | Each is narrowed to its documented size before any field is read, so a truncated file fails at the window rather than four reads later. |
| T-02-14 | Information disclosure | `lpPrivateObject` read as an address when it is `-1` | medium | mitigate | The field is read as a raw `u32` and the sentinel is matched before anything resolves it, so `0xFFFFFFFF` is never handed to the address resolver. |
</threat_model>
